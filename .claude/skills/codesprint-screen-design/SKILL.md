# CodeSprint 화면 디자인

이 화면은 **문제를 푸는 사람의 작업대**다. 소개 페이지도, 대시보드 데모도 아니다.
사용자는 한 번 들어오면 한 시간씩 문제 본문을 읽고 코드를 친다. 그래서 기준은
"눈에 띄는가" 가 아니라 **"오래 봐도 피곤하지 않고, 필요한 것이 제자리에 있는가"** 다.

## 정본은 지금의 app.css 다

새 규칙을 만들기 전에 이미 있는 것을 따른다. `app.css` 첫 주석이 이 화면의 원칙이다.

```
그림자를 쓰지 않는다. 영역은 1px 경계와 배경 명도로만 나눈다.
색은 강조색 하나(파랑)와 판정을 구분하는 초록/빨강뿐이다.
```

| 무엇 | 쓰는 것 | 이유 |
| --- | --- | --- |
| 배경 단계 | `--bg` → `--panel` → `--raise` | 층은 명도로만 나눈다. 그림자는 층을 떠 보이게 해 밀도를 깬다 |
| 구분선 | `1px solid var(--line)` | 영역 경계는 이것 하나 |
| 글자 | `--ink` / 보조는 `--muted` | 회색을 새로 만들지 않는다 |
| 강조 | `--accent` 하나 | 누를 수 있는 것, 지금 선택된 것 |
| 판정 | `--ok` / `--bad` | **판정에만** 쓴다. 장식에 초록·빨강을 쓰면 판정과 헷갈린다 |
| 둥글기 | `4px` 이하, 탭·패널은 `0` | 둥근 카드는 이 화면의 밀도와 맞지 않는다 |
| 코드·수치·ID | `var(--mono)` | 코드, 실행 시간, 메모리, Skill ID, 문제 code |
| 크기 | 본문 14px, 보조 12~13px, 제목 15px 이하 | 큰 제목이 필요한 화면이 아니다 |

**새 색 · 새 그림자 · 새 폰트를 넣고 싶어지면 멈추고 이유를 적는다.** 대부분은 기존
토큰으로 된다. 정말 필요하면 `:root` 에 토큰으로 추가하고, 그 자리에서 한 줄 주석으로
무엇에만 쓰는지 적는다.

## 레퍼런스: 코딩테스트 서비스의 관례

사용자는 이미 백준 · 프로그래머스 · LeetCode 에 익숙하다. 거기서 굳어진 자리를
바꾸면 기능이 같아도 "어디 있지?" 가 된다. 그대로 따를 것은 **배치와 표기의 관례**다
(색이나 로고 같은 브랜드 요소는 따라 하지 않는다).

- **왼쪽 문제, 오른쪽 에디터.** 본문 · 입출력 예시가 왼쪽, 코드와 실행 · 제출이 오른쪽
  아래. 가운데 경계는 끌어서 너비를 바꾼다
- **입력 / 출력 예시는 나란히, 고정폭 글꼴로.** 복사해서 바로 붙일 수 있게 앞뒤 공백을
  건드리지 않는다
- **실행과 제출은 다른 버튼이다.** 실행은 예시만 돌리고 기록을 남기지 않는다(ADR-0020).
  제출이 주 버튼(`primary`), 실행은 보조
- **판정은 짧은 코드 + 색.** `ACCEPTED` 초록, 나머지 판정은 빨강. 판정 문자열은 서버가
  준 그대로 쓰고 번역하거나 바꿔 적지 않는다
- **숫자는 단위와 함께 표로.** `90 ms`, `20480 KB`, `5 / 6` 처럼. 문장 안에 녹이지 않는다
- **메타 한 줄.** 문제 제목 아래 시간 제한 · 메모리 제한 · 종류를 한 줄의 `--muted` 로
- **힌트와 해설은 접혀 있다가 사용자가 연다.** 먼저 보여주지 않는다. 마지막 칸(전체
  풀이)은 무엇을 여는지 버튼 이름이 분명히 말한다

이 화면에만 있는 것(다음 행동, Skill 상태, 복습, 개념 자료)도 같은 문법을 쓴다 —
짧은 라벨, 고정폭 코드, `--muted` 보조 설명.

## AI 티 금지 목록

아래는 "생성된 화면" 처럼 보이게 만드는 흔한 패턴이다. 이 화면에서는 쓰지 않는다.
하나라도 쓰려면 왜 필요한지 주석으로 남긴다.

**모양**

- 보라 · 남색 · 분홍 **그라데이션** (배경, 버튼, 글자 모두)
- `box-shadow` 로 띄운 카드, 호버 시 떠오르는 효과
- 큰 둥근 모서리(8px 이상)의 카드 격자, 알약 모양 버튼 남발
- 글래스모피즘(`backdrop-filter: blur`), 반투명 겹침
- 제목 옆 **이모지**, 섹션마다 붙는 의미 없는 아이콘
- 빛나는 테두리, 네온, 두근거리는 애니메이션, 시선을 끄는 전환 효과
- 한 화면에 강조색 여러 개, 상태마다 다른 파스텔 배지
- 가운데 정렬된 큰 히어로 문구와 빈 여백
- 점수를 **원형 게이지 · 진행 막대 · 별점**으로 부풀리기. mastery 는 `0.82` 처럼 숫자로
  두고, 계산하지 않았으면 `–` 다(ADR-0009 의 null / 0.0 구분을 화면이 흐리면 안 된다)

**구조**

- 비어 있을 때 쓰는 일러스트 · 큰 아이콘. 한 줄 `--muted` 문장으로 충분하다
- 기능 소개용 카드 3개 나열
- 토스트가 화면 모서리에서 튀어나오는 알림. 결과는 결과 패널 제자리에 쓴다

## 문구 규칙

화면 문구는 **사실을 짧게** 말한다. 이 저장소의 커밋 · 주석 말투와 같다.

**쓰지 않는 말**

| 쓰지 않는다 | 이유 | 대신 |
| --- | --- | --- |
| "강력한", "스마트한", "혁신적인", "원활한", "최적의" | 무엇도 설명하지 않는 형용사 | 무엇을 하는지 적는다 |
| "AI 가 분석해 드립니다", "맞춤형 학습 경험" | 마케팅 말투. 그리고 판단은 AI 가 아니라 시스템이 한다(ADR-0001) | "오답 원인 후보", "다음 행동" |
| "잘하셨어요! 🎉", "아쉬워요 😢", "화이팅!" | 감정 연출. 매 제출마다 반복되면 소음이다 | 판정만 적는다 |
| "~해 드릴게요", "~하실 수 있어요" | 과한 존대가 문장을 길게 만든다 | "~한다", 명사형 라벨 |
| "잠시만 기다려 주세요..." 같은 말줄임표 대기 문구 | 무엇을 기다리는지 말하지 않는다 | "채점 중" |
| "오류가 발생했습니다" | 무엇이 왜 실패했는지 없다 | 서버가 준 이유를 그대로 |

**쓰는 방식**

- **버튼은 무엇이 일어나는지 짧게.** 지금 화면의 "제출 후 채점하기", "예제로 실행",
  "다음 힌트 (H2)", "새로 시작" 정도가 기준이다. 이보다 길어지면 설명을 버튼 밖으로 뺀다
- **안내는 한 문장.** 무엇이 일어났고 사용자가 할 일이 있으면 그것까지
- **서버가 준 이유를 덮지 않는다.** `reason` 이 있으면 그대로 보여준다. 화면이 부드럽게
  바꿔 쓰면 기록에 남은 판단과 사용자가 본 말이 달라진다
- **판정 · Skill ID · 행동 이름은 원문 코드 그대로.** `WRONG_ANSWER`, `BFS_GRID_TRAVERSAL`,
  `REVIEW_CONCEPT`. 옆에 한국어 설명을 붙이는 것은 되지만 코드를 지우지 않는다
- **숫자는 화면이 만들지 않는다.** "채점 기록에 남는 단계: H3" 의 3 은 서버 값이다.
  화면이 세거나 반올림하면 사용자가 보는 값과 기록되는 값이 갈린다(ADR-0027)

## 고치기 전에 확인할 것

화면 규칙은 모양 말고도 검사로 지켜지고 있다. 디자인을 바꾸다 이것들을 깨지 않는다.

- **새 비동기 요청은 표를 받는다**(`claimView`, ADR-0023). 받지 않으면 `WebClientTest` 가 막는다
- **새 `/api/` 경로는 실재해야 한다.** `WebClientTest` 가 method 까지 대조한다
- **E2E stub 은 계약을 지난다**(ADR-0025). 새 응답을 stub 하면 `e2e/fixtures/contracts.js` 에 잇는다
- **외부 폰트 · 라이브러리를 추가하지 않는다.** 빌드 도구가 없는 화면이다(ADR-0017).
  꼭 필요하면 버전 고정 + integrity 가 있어야 하고 `WebClientTest` 가 본다

## 마무리할 때

바꾼 화면을 한 번 떠올려 보고 스스로 묻는다.

1. 새로 들어간 색 · 그림자 · 둥근 모서리가 위 표 밖인가?
2. 금지 목록의 모양이나 말이 하나라도 들어갔는가?
3. 서버가 준 값(판정, 이유, 단계, mastery)을 화면이 바꿔 적었는가?
4. 백준이나 LeetCode 를 쓰던 사람이 이 화면에서 제출 버튼과 예시를 바로 찾는가?

하나라도 걸리면 고친 뒤 끝낸다.
