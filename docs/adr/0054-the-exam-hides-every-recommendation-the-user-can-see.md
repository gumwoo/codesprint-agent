# ADR-0054 · 시험은 사용자가 볼 수 있는 추천을 전부 가리고, 진단은 한 계산으로 묻는다

- 상태: 채택
- 날짜: 2026-09-27
- 정본 근거: PRD §84(Mock Test Mode), [ADR-0035](0035-a-learning-track-scopes-the-skill-graph.md),
  [ADR-0038](0038-the-plan-is-decided-not-generated.md), [ADR-0043](0043-mock-test-and-learning-modes.md),
  [ADR-0049](0049-analytics-exam-strategy-evaluator.md)

## 맥락

검증 에이전트가 두 결함을 재현했다.

**1. 시험 전에 낸 일반 제출이 시험 문제의 유형을 알려 줬다.** INTRO 사용자가 진단을 WA 로 따라가다 진단이 끝난 걸음에서
마지막 제출의 다음 행동이 `CHANGE_SKILL PYTHON_LIST_BASIC → P11_LIST_BASIC` 이었고, 바로 만든 모의 시험에 P11 이 들어갔다.
ADR-0043 은 시험에서 낸 제출의 일반 조회(`GET /api/submissions/{id}`)만 409 로 닫았다. 시험 전 일반 제출의 조회는 시험
중에도 200 으로 `nextAction.targetSkill` · `skillUpdates` 를 줬다. 다음 문제(`next-problem`)는 이미 사용자 기준으로 닫고
있었다 - 같은 정보를 두 엔드포인트가 다른 기준으로 닫았다.

**2. 트랙을 바꾼 사용자에게 계획과 진단 패널이 다른 문제를 가리켰다.** ALGORITHM → INTRO 사용자에게 진단 패널은 P23,
오늘의 계획 DIAGNOSE 블록은 P31 이었다(3/3). 패널(`DiagnosticService.nextStep(userId)`)과 결과의 다음 행동
(`JudgeResultApplier`)은 트랙 안을 묻되 함의를 전체 Evidence 에서 구하는데(ADR-0035 §3-1), 오늘의 계획과 모의 시험 후보의
`reserved` 는 트랙 안 목록 하나만 넘겨 함의도 트랙 안에서만 구했다. ADR-0038 은 계획과 진단이 다른 곳을 가리키지 않게
하라고 했고, `reserved` 는 계획이 가리킨 문제만 빼서 패널이 가리킨 문제는 시험에 들어갈 수 있었다.

## 결정

### 1. 시험 중에는 제출한 사용자 기준으로 제출 조회를 닫는다

`MockTestService.hidesUntilEnd(submissionId)` 는 **그 제출을 낸 사용자가 시험 중인지**를 본다. 시험에서 낸 제출이든 시험 전
일반 제출이든 시험이 끝날 때까지 `GET /api/submissions/{id}` 와 `next-problem` 이 409 다. 두 엔드포인트가 이 판단 하나를
쓴다. 제출 조회(`GET /api/submissions/{id}`)의 409 에는 이유 문장을 싣는다 - 화면이 시험 전 제출의 채점을 기다리고 있었다면
결과가 오지 않는 이유를 알아야 한다. `next-problem` 의 409 는 전처럼 본문이 없다.

### 2. 마지막 일반 제출이 가리킨 다음 문제는 시험 후보에서 뺀다

다음 행동이 정해진 가장 최근의 일반 제출(`mock_test_events` 에 없는 제출)의 `next_problem_code` 를 `reserved` 에 더한다.
진단 · 만기 복습이 가리키는 문제를 빼는 것(ADR-0049)과 같은 자리다.

### 3. 진단을 묻는 곳은 전부 같은 계산을 쓴다

`MasteryService.scopedStatesOf(userId)` 가 전체 상태를 한 번 계산하고 트랙 안을 걸러 둘을 함께 준다(`Scoped`). 진단 패널 ·
오늘의 계획 · 시험 후보(`create` · `upcoming` 둘 다)가 이것으로 `DiagnosticService.nextStep(Scoped)` 를 부른다. **트랙 안
목록 하나만 받는 `nextStep(List)` 는 지웠다** - 있으면 다시 누군가 그것을 부른다. 결과 반영(`JudgeResultApplier`)은 이미
`nextStep(states, all)` 로 같은 계산을 하고 있어 그대로 둔다.

트랙 안 상태를 전체 상태에서 거르면 선수 판단이 전체 mastery 를 본다는 점이 `statesOf` 와 다르지만, 트랙 안 Skill 의 선수는
트랙 안에 있으므로(tracks.yaml 규칙 1, CI 가 막는다) 상태가 같다.

## 고른 것과 버린 것

결함 1 에는 두 길이 있었다.

| | (a) 시험 중 제출 조회를 닫는다 | (b) 그 문제를 시험 후보에서 뺀다 |
| --- | --- | --- |
| 막는 것 | 시험 **중** 에 조회로 보는 것. 후보를 어떻게 고르든 막는다 | 시험 **전** 에 결과 패널로 이미 본 문제가 시험에 드는 것 |
| 막지 못하는 것 | 시험을 만들기 전에 결과 패널이 이미 보여 준 문제 - 이미 본 것은 닫을 수 없다 | 시험 중 조회의 `skillUpdates` · `review` 등 다음 문제 밖의 정보 |
| 비용 | 시험 전에 낸 제출의 채점 결과를 시험이 끝날 때까지 못 본다 | 후보가 하나 줄어 트랙 초반에는 시험이 짧아지거나 409 가 될 수 있다 |

둘은 막는 구간이 달라 **둘 다 한다.** (a) 만 하면 재현된 상황 그대로 - 결과 패널이 P11 을 보여 준 직후 만든 시험에 P11 이
든다. (b) 만 하면 시험 중 조회가 계속 학습 상태를 보여 준다. ADR-0043 이 일반 제출을 시험 중에 받지 않기로 한 이유(시험
제출이 바꾼 before 값이 실린다)가 조회에도 그대로 적용된다.

(b) 는 `create` 와 `upcoming` 이 같은 `candidates → reserved` 를 거치므로 두 길에 같이 들어간다 - "계획의 모의 시험 분 = 실제
시험 분"(TodayTest)이 유지된다. 뺄 값은 결과를 반영할 때 제출 행에 얼린 것이라 두 호출이 같은 값을 읽는다.

결과 패널의 다음 문제를 계획이나 결과 쪽에서 바꾸는 길은 택하지 않았다 - 다음 행동은 반영 시점에 고정된다(ADR-0002).
시험 쪽에서 빼는 것이 ADR-0049 가 진단 블록을 지킨 방식과 같다.

## 검증

| 검사 | 무엇을 보는가 | 되돌리면 |
| --- | --- | --- |
| `MockTestTest.theLastNormalSubmissionDoesNotLeakIntoTheTest` | INTRO 진단을 WA 로 따라가며 걸음마다 시험을 만든다. 다음 문제가 뺄 목록에 있고 시험에 없다, 시험 중 제출 조회 409 · 이유 문장, 끝나면 200 | (a) 를 되돌리면 걸음 1 에서 200. (b) 를 되돌리면 걸음 14(CHANGE_SKILL → P11)에서 뺄 목록이 비고, 그 시험에 P11 이 들었다 |
| `TodayTest.planAndPanelAgreeAfterATrackSwitch` | ALGORITHM 에서 1~3 걸음 뒤 INTRO 로 바꾸고 진단을 따라가며, 계획의 DIAGNOSE = 패널, 패널 문제가 뺄 목록에 있고 시험에 없다 | 계획 쪽을 되돌리면 P23 ≠ P31, 시험 쪽을 되돌리면 뺄 목록에 P31 만 있다 |

뺄 목록은 `MockTestService.reservedProblemCodes` 로 본다. 뺀 문제가 실제 시험에 들지는 구성 규칙(네 자리 · 도메인 중복
없음)이 정하므로, 시험만 보면 빼는 계산이 틀려도 통과하는 경우가 많다 - 시험 쪽 계산을 되돌린 채 트랙 전환 시나리오
36 명으로 시험 208 개를 만들었는데 패널 문제가 시험에 든 적은 없었다 - 불일치가 난 걸음의 패널 문제는 상당수가 LOCKED 라
후보가 아니었고, 후보인 것은 구성 규칙이 고르지 않았다. 그래서 목록을 직접 보고, 시험은 함께 본다.

## 후속 - 화면이 시험의 뒷자리를 치운다

아래 두 결함은 이 결정 전부터 있었고, 검증 에이전트가 재현했다.

**1. 시험 때문에 가려진 결과를 끝난 뒤 찾아갈 수 있게 한다.** 시험 전에 낸 일반 제출의 조회가 409 가 되자 화면은 연결
실패와 같이 세 번 센 뒤 "결과를 가져오지 못하고 있다(409 이유). 서버가 돌아오면 여기에 나타난다" 를 보였다 - 서버 장애로
읽혔다. 그리고 시험 문제를 열면 폴러가 끊겨(`openMockProblem` → `cancelActivePolling`) 끝난 뒤에도 결과가 오지 않았다.

- 제출 조회가 409 면 세지 않고 곧바로 **서버의 이유를 그대로** 싣고, 제출은 접수됐으며 끝나면 여기나 모의 시험 탭에서
  본다고만 덧붙인다. 이 엔드포인트의 409 는 시험 하나뿐이라 상태 코드만 본다 - 시험 중인지를 화면이 따로 판단하지 않는다
- 관찰을 놓게 되는 두 곳에서 그 제출을 **사용자별로 하나** 적어 둔다(`withheldSubmissions`) - 폴러가 409 를 받았을 때, 그리고
  시험 문제를 열면서 아직 결과를 그리지 않은 일반 제출의 관찰을 놓을 때. 뒤의 것이 있어야 폴러가 409 를 보기 전에 시험
  문제를 연 경우가 남지 않는다
- 모의 시험 탭이 **진행 중인 시험이 없다는 서버 응답**(없음 · `FINISHED`)을 받았을 때만 "결과 보기" 를 보인다. 누르면 그
  제출의 문제를 열고(`openProblem` 이 문제 화면의 표를 받는다) 그 결과를 관찰한다. 결과를 그리면 적어 둔 것을 지운다

| | 고른 것 | 버린 것 |
| --- | --- | --- |
| 어디서 권하나 | 모의 시험 탭 - 시험을 끝내는 버튼이 거기 있고, 끝났는지는 그 탭이 서버에 묻는다 | 결과 패널에 곧바로 그리기 - 그 사이 연 다른 문제의 화면을 덮고, 설명해 보기 · 다음 단계가 지금 열린 문제를 가리킨다 |
| 무엇을 여나 | 그 제출의 문제와 결과를 함께 | 결과만 - 결과 패널은 문제 화면의 것이다 |
| 얼마나 적나 | 사용자별 하나 - 새 제출이 관찰을 넘겨받는 지금 규칙(마지막 하나만 본다)과 같다 | 제출 이력 화면 - 범위가 커진다 |

시험과 관계없이 다른 문제를 열어 관찰을 놓는 것은 그대로다 - 그때는 사용자가 기다릴 수 있었다. 시험은 끝날 때까지
기다릴 수 없게 만드므로 그 경우만 적는다.

**2. 사용자를 바꾸면 이전 사용자의 시험 문제를 놓는다.** 시험 문제를 열어 둔 채 사용자를 바꾸면 그 본문과
"시험 · 문제 A" 가 새 사용자 화면에 남고 제출 · 실행 버튼이 눌렸다. 서버는 남의 시험을 이미 404 로 막는다(`owned`) -
새 사용자의 id 로 나가므로 이전 사용자의 시험에 들어가지는 않았다. `switchedUser` 가 시험을 끝낼 때와 같은 방식
(`releaseExamProblem`)으로 문제를 놓고, 문제 화면을 보고 있었으면 목록으로 보낸다. 일반 문제는 누구의 것도 아니라
그대로 둔다(ownership.spec.js 의 버튼 테스트가 그 전제로 돈다).

| 검사 | 되돌리면 |
| --- | --- |
| `exam-leftovers.spec.js` 사용자 전환 | 이름표가 "시험 · 문제 A" 로 남는다. 놓기만 하고 목록으로 보내지 않으면 본문이 보인다 |
| 〃 409 문구 | 세 번 센 뒤 "서버가 돌아오면" 문구 |
| 〃 시험 문제를 연 뒤 | "결과 보기" 가 없다(조회를 붙잡아 폴러가 409 를 보기 전에 연다). 시험 중에도 권하면 여기서 걸린다 |
| 〃 409 를 본 뒤 다른 문제 | 409 를 받은 쪽이 적지 않으면 "결과 보기" 가 없다 |
| 〃 사용자별 | 다른 사용자의 기록을 권한다. 원래 사용자로 돌아오면 권하는 대조가 함께 있다 |
| `MockTestTest.othersTestIsNotFound` | 남의 시험으로 제출 · 실행 · 끝내기가 404 인지, 제출 행이 남지 않는지. 제출에서 소유 확인을 빼면 202 |

E2E stub 이 409 본문을 내야 해서 거절 본문의 계약(`api-error.schema.json`)을 두었다. `fulfill` 은 4xx 를 경로의 계약이
아니라 이 계약에 대고 보고, `MockTestTest` 가 실제 409 본문을 같은 계약으로 본다.

## 남는 위험

- 시험에서 낸 제출의 다음 문제는 빼지 않는다. 결과 패널은 일반 제출에만 뜨지만, 시험이 끝난 뒤 조회 API 로는 볼 수 있다
- 가장 최근 하나만 뺀다. 그 전 제출의 결과 패널을 사용자가 기억하고 있으면 그 문제는 시험에 들 수 있다
- 가려진 결과를 적어 둔 것은 브라우저 메모리다. 시험 중에 새로 고치면 사라지고, 시험 시간이 다 돼 저절로 끝나면 모의
  시험 탭을 다시 열어야 "결과 보기" 가 보인다. Evidence 와 다음 행동은 DB 에 반영되므로 학습 상태를 잃지는 않는다
