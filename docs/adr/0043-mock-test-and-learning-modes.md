# ADR-0043 · 모의 시험과 학습 모드 - 시험은 고르지 않고 결정하며, 관측한 시각만 평가한다

- 상태: 채택
- 날짜: 2026-09-26
- 정본 근거: PRD §82(시험 직전 모드), §84(Mock Test Mode), §85(시간 관리 평가), §86(문제 선택 능력),
  §151(학습 모드), [ADR-0001](0001-llm-analyzes-system-decides.md), [ADR-0027](0027-hint-level-is-observed-not-reported.md),
  [ADR-0034](0034-the-road-to-the-full-prd.md), [ADR-0038](0038-the-plan-is-decided-not-generated.md)

## 맥락

ADR-0034 의 W7 이다. 시험 직전 모드(D-7 이하에서 계획이 바뀐다)는 ADR-0038 의 `DailyPlanner` 가 이미 한다.
남은 것은 모의 시험과 학습 모드다.

PRD §85 는 시간 관리를 "문제 읽기 시간 · 첫 코드 작성 시간 · 첫 실행 시간 · 첫 실패 이후 수정 시간 · 최종 제출
시간" 으로 나눈다. 이 중 **서버가 관측할 수 있는 것은 사용자가 서버에 무언가를 보낸 순간뿐이다** - 문제를
연 순간, 실행한 순간, 제출한 순간. 읽기가 언제 끝나고 코드를 언제 쓰기 시작했는지는 알 수 없다.

## 결정

### 1. 시험 문제는 시스템이 고른다

`MockTestComposer` 는 순수 함수다. 사용자의 트랙 안에서, 한 번도 제출한 적 없는 문제 가운데 PRIMARY Skill 이
LOCKED 가 아닌 것을 후보로 둔다. 후보를 기대 풀이 시간 순으로 세우고 네 곳(가장 쉬운 것 · 1/3 · 2/3 · 가장
어려운 것)에서 고른다. **도메인이 겹치지 않게** 다음 후보로 넘긴다. 후보가 둘보다 적으면 시험을 만들지
않는다(409) - 한 문제짜리 시험으로는 문제 선택을 볼 수 없다.

- 라벨(A, B, C, D)은 **문제 번호 순**이다. 난이도 순으로 붙이면 "쉬운 것부터" 가 라벨을 읽는 것으로 끝난다
- 시험 시간은 네 문제의 기대 풀이 시간의 합이다(30~180 분으로 자른다). LLM 에게 묻지 않는다
- 시험 중에는 **유형을 보여 주지 않는다** - 문제 code 에도 유형이 들어 있으므로(P80_DIRECTED_SHORTEST_...)
  code · 제목 · Skill 을 모두 숨기고 라벨로만 부른다. 본문 · 제한 · 예시만 준다

### 2. 시험 중에는 도움을 주지 않는다(PRD §84)

- 힌트는 409 다. 그 문제가 진행 중인 시험에 들어 있으면 문제 code 로 직접 불러도 막는다
- 제출 결과는 판정만 준다. 일반 조회(`GET /api/submissions/{id}`)는 시험이 끝날 때까지 409 다 - 거기에는
  Reviewer 분석과 다음 행동이 있다. 다음 문제(`next-problem`)도 같다
- Evidence 는 평소처럼 쌓는다. 시험에서 낸 제출도 실제 풀이다. 힌트를 막았으므로 도움 없는 풀이로 기록된다
- **그래서 시험 중에는 학습 상태 · 추천 화면을 닫는다(409).** 오늘의 계획 · 진단 · 다음 문제는 시험 문제와 같은
  조건(처음 보는 · 잠기지 않은 문제)으로 고르므로 시험 문제를 code 와 제목째 추천했고, 시험 제출 전후의 Skill
  지도를 비교하면 그 문제의 유형이 드러났다(검증 에이전트가 재현했다). 오늘 · 오답 · Skill 지도 · 복습 · 진단 ·
  다음 문제, 그리고 시험 문제를 code 로 여는 것을 한 곳(`ExamLock`)에서 닫는다. Evidence 반영을 끝날 때까지
  미루는 대신 화면을 닫은 이유는, 미루면 채점 결과를 붙들어 둘 자리와 끊긴 반영을 다시 이을 규칙이 더 생기기
  때문이다. 시험이 끝나면 바로 열린다
- **시험 중에는 일반 제출도 받지 않는다(409).** 시험 밖 문제라도 그렇다 - 그 결과의 `skillUpdates` 에는 시험
  제출이 바꾼 before 값이 실려, 닫아 둔 Skill 지도 대신 시험 문제의 유형을 알려 준다(검증 에이전트가 재현했다).
  실행(`run`)은 시험 밖 문제면 받는다 - 실행 결과에는 Skill 값이 없다

### 3. 관측은 시험 표 안에서, 한 시계로

열기 · 실행 · 제출은 시험 전용 엔드포인트로만 받고, 그 순간을 `mock_test_events` 에 **주입된 시계**로 남긴다.
실행 큐(`judge_jobs.created_at`)는 DB 시계라 테스트가 옮길 수 없고, 두 시계를 섞으면 "시작 후 몇 초" 가 틀린다.

**여는 것도 POST 다.** 연 시각이 곧 기록이므로 조회가 아니라 상태 변경이다 - GET 으로 두면 미리 불러오기가
문제를 연 것으로 기록한다(힌트와 같은 이유, ADR-0027).

### 4. 끝난 뒤 보고서는 관측한 것만 말한다

문제마다 연 시각 · 첫 실행 · 첫 제출 · 푼 시각(처음 ACCEPTED 를 낸 제출 시각)을 시작 후 초로 주고, 결과를
다섯 중 하나로 가른다 - `SOLVED` · `JUDGING`(낸 제출이 아직 채점 중이다) · `ATTEMPTED`(낸 것이 전부 채점됐고 못
풀었다 = 버린 문제) · `OPENED`(열고 내지 않았다) · `UNOPENED`. 끝나기 직전에 낸 제출은 끝난 뒤에 채점되므로, 그
전까지 "못 풀었다" 로 단정하지 않는다. 그 문제에서 나온 실수(Reviewer 탐지와 시스템이 매긴 상태)를 붙인다.

전략은 사실로만 적는다.

| 항목 | 뜻 |
| --- | --- |
| `openOrder` | 연 순서(라벨) |
| `easiestFirst` | 처음 연 문제가 기대 풀이 시간이 가장 짧은 문제인가. 아무것도 안 열었으면 null |
| `overExpected` | 연 뒤 푼 때(못 풀었으면 시험 끝)까지가 기대 풀이 시간을 넘었는가 |

**재지 않는 것:** 읽기 시간과 첫 코드 작성 시간은 나누지 않는다 - 둘 다 "연 뒤 첫 실행까지" 안에 있고 서버는
그 사이를 볼 수 없다. **알고리즘 인식**도 판정하지 않는다 - AC 는 Skill 사용을 증명하지 않고(ADR-0033), 틀린
풀이가 무엇을 알아봤는지는 Reviewer 의 주장일 뿐이다. 그래서 보고서에 이 항목들이 없다. 없는 값을 어림해
채우면 사용자는 그것을 관측으로 읽는다.

### 5. 학습 모드는 "무엇을 내주는가" 만 바꾼다

| 모드 | 힌트 | 문제 화면 |
| --- | --- | --- |
| `GUIDED` | H1~H6 | PRIMARY Skill 의 개념 자료를 함께 준다 |
| `NORMAL` | H1~H6 | 지금과 같다 |
| `STRICT` | H1~H2 | 지금과 같다 |
| `EXAM` | 없음 | 문제 화면의 Skill 목록을 숨긴다(null). 문제 code · 제목 · 목록의 PRIMARY Skill 은 그대로다 - 모의 시험처럼 숨기려면 시험으로 연다 |
| `FREE` | H1~H6 | 지금과 같다. 자유 질문은 Tutor 로 따로 연다 |

**다음 행동 · mastery 계산은 모드로 바뀌지 않는다.** 모드가 결정을 바꾸기 시작하면 같은 풀이 기록에서 모드에
따라 다른 학습 경로가 나와 규칙을 검증할 수 없다(ADR-0002). 모드는 사용자에게 주는 도움의 양만 정한다.

모드를 바꾸면 **이미 본 힌트도 그 모드의 상한을 따른다.** NORMAL 에서 H3 까지 본 뒤 STRICT 로 바꾸면 H3 을 다시
열 수 없다(H1 · H2 는 연다). 본 기록(hint_usage)은 그대로 남는다 - 관측이기 때문이다.

기본값은 `NORMAL` 이다 - PRD §151 이 "기본" 이라고 적은 모드다. 트랙에 기본값을 두지 않은 것(ADR-0035)과
다른 이유는, 목표는 사용자만 알지만 도움의 양은 고르지 않았을 때 쓸 표준이 PRD 에 정해져 있기 때문이다.

## 결과

```
POST /api/users/{id}/mock-tests                      시험을 만든다(201, 진행 중인 시험이 있으면 409)
GET  /api/users/{id}/mock-tests/latest                가장 최근의 시험(없으면 404)
GET  /api/mock-tests/{id}?userId=                    상태 · 남은 시간 · 라벨별 진행
POST /api/mock-tests/{id}/problems/{label}/open      문제를 연다(연 시각을 남긴다)
POST /api/mock-tests/{id}/problems/{label}/run       예시로 실행
POST /api/mock-tests/{id}/problems/{label}/submit    제출(끝난 뒤에는 409)
GET  /api/mock-tests/{id}/submissions/{sid}?userId=  판정만
POST /api/mock-tests/{id}/finish                     일찍 끝낸다
GET  /api/mock-tests/{id}/report?userId=             보고서(끝나기 전에는 409)
PUT  /api/users/{id}/learning-mode                   학습 모드
```

## 남는 위험

- 시험 시간이 지나면 따로 끝내지 않아도 끝난 것으로 본다. 끝난 뒤 들어온 제출은 409 로 막는다. 이미 큐에 들어간
  제출의 판정은 끝난 뒤에 붙을 수 있고, 그동안 그 문제는 `JUDGING` 이다 - 판정이 붙으면 보고서가 바뀐다
- 후보가 둘 이상 넷 미만이면 그 수만큼으로 시험을 만든다. 트랙 초반의 사용자는 짧은 시험을 받는다
- **409 로 시험 문제를 가려낼 수 있다.** `GET /api/problems/{code}?userId=` 는 시험 문제에만 409 를 준다. 목록과
  대조해 하나씩 찔러 보면 어느 문제가 시험 문제인지 알 수 있다. 공개 저장소 · 자기 PC 에서 도는 앱이라 일부러
  자기 시험을 무너뜨리는 경우만 남는다고 보고 막지 않았다 - 막으려면 모든 문제를 시험 중에 닫아야 한다
- 판정이 `SYSTEM_ERROR` 인 제출도 "냈지만 못 풀었다"(ATTEMPTED)로 센다. 사용자의 실패가 아니지만 보고서의
  결과 칸을 하나 더 두지 않았다 - 보고서 표에 판정 이력은 없으므로 그 문제를 다시 보는 것으로 확인한다
- 학습 모드 칸은 읽기(`loadLearningMode`)와 저장이 다른 통을 쓴다. 저장 중에는 읽지 않고, 저장이 시작되면
  그 전에 떠난 읽기를 버린다. 모드를 적는 곳은 `applyLearningMode` 하나다 - 칸 · 튜터 표시 · 모드 변수를
  따로 적으면 한쪽만 맞는다(검증 에이전트가 두 번 재현했다). 저장 응답이 버려지면(그 사이 사용자가 바뀌었으면)
  또는 저장이 실패하면 지금 사용자의 모드를 다시 읽는다 - 저장 중에 건너뛴 읽기를 누군가는 해야 한다
  읽기가 실패하면(없는 사용자 · 연결 실패) 모드를 비운다 - 이전 사용자의 FREE 로 튜터 칸이 남지 않게
- **시험 중에도 시험 밖 문제의 힌트 · 실행은 받는다.** 두 응답에는 학습 상태 값이 없다. 다만 문제 목록에
  `primarySkill` 이 보이므로 시험 문제와 같은 유형의 다른 문제 힌트를 골라 볼 수 있다 - PRD §84 의 "도움을
  주지 않는다" 를 넓게 읽으면 이것도 도움이다. 막으려면 시험 중 모든 힌트를 닫아야 하고, 그 결정은 미뤘다
