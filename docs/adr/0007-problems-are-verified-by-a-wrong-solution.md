# ADR-0007 · 문제마다 틀린 풀이를 함께 두고, 그것이 걸리는지 검사한다

- 상태: 채택
- 날짜: 2026-09-05
- 정본 근거: Addendum §40, §66, §133 / PRD §143

## 맥락

문제와 Test Case가 생겼다. 이것이 맞는지 어떻게 확인하는가.

가장 자연스러운 답은 "정답 풀이를 돌려서 AC가 나오면 된다"다. Addendum §133의
Problem Validator도 `Reference Solution 성공`을 항목으로 둔다.

그런데 그것만으로는 **아무것도 거르지 못하는 Test Case 집합**이 통과한다.

```json
{ "cases": [ { "input": "", "expectedOutput": "" } ] }
```

이 문제는 reference를 통과시킨다. 그리고 **모든 제출을 통과시킨다.**

극단적인 예처럼 보이지만, 실제로 흔한 형태는 이렇다.

- sample case만 있고 경계 case가 없다
- 모든 case의 답이 같아서 상수를 출력해도 AC가 난다
- 격자가 전부 대칭이라 방향을 잘못 써도 답이 같다

이건 저장소의 다른 곳에서 이미 두 번 마주친 문제다.

```text
계약 하네스   검사가 통과하는 것과 검사가 일하는 것은 다르다  → 메타테스트
Judge 격리    옵션을 적어둔 것과 실제로 막히는 것은 다르다     → 대조군
문제 데이터   정답이 통과하는 것과 오답이 걸리는 것은 다르다   → 이 ADR
```

## 결정

**문제마다 `wrong.py`를 함께 두고, 그것이 실제로 걸리는지 CI가 확인한다.**

```text
reference.py 가 ACCEPTED 인가      정답이 정답으로 판정되는가
wrong.py 가 걸리는가                이 Test Case 가 오답을 실제로 거르는가
```

둘째가 통과하지 못하면 `[VACUOUS]`로 실패시킨다.

`wrong.py`는 아무렇게나 틀린 코드가 아니라 **그 문제에서 실제로 자주 나오는 실수**다.
`problem.yaml`의 `commonMistakes`와 짝을 이룬다. 무엇을 틀리게 했는지 파일 첫 줄
주석에 적는다.

| 문제 | wrong.py 가 저지르는 실수 |
| --- | --- |
| P01 | 큐가 비었을 때 `-1`을 내지 않고 건너뛴다 |
| P02 | 도달 여부를 따지지 않고 전체 1의 개수를 센다 |
| P03 | 대각선까지 이어진 것으로 본다 |
| P04 | 첫 영역만 재고 멈춘다 |
| P05 | 큐 대신 스택을 쓴다 |
| P06 | 위/왼쪽만 검사하고 아래/오른쪽 경계를 빠뜨린다 |
| P07 | 상한만 보고 하한(음수)을 보지 않는다 |
| P08 | 방문 처리를 꺼낼 때 한다 |
| P09 | 대각선 이동을 빠뜨린다 |
| P10 | 도달 여부를 무시하고 맨해튼 거리 최대를 고른다 |

## 왜 이것이 mastery와 직결되는가

측정하지 못하는 문제로 쌓은 Evidence는 mastery를 오염시킨다.

틀린 풀이가 AC를 받으면 `independent_score`가 0.95로 올라간다(Addendum §11.1).
그 값은 EMA로 누적되고, `MASTERED` 판정에 쓰이고, Decision Engine이 `UNLOCK_NEXT`를
고르는 근거가 된다. **문제 하나의 결함이 학습 경로 전체를 잘못된 방향으로 민다.**

PRD §143이 "이 서비스가 실패하는 가장 쉬운 방법"으로 든 것 중 하나가
"문제마다 Target Skill이 존재한다"인데, Target Skill이 있어도 그것을 **측정하지
못하면** 같은 결과가 된다.

## 설계 중 알게 된 것 — P08

평범한 격자 BFS에서 **방문 시점 오류는 보통 답을 바꾸지 않는다.** 같은 칸이 큐에
여러 번 들어가 느려질 뿐, 최단거리 자체는 맞게 나온다.

처음 만든 P08의 `wrong.py`(방문 처리를 pop 시점에 하는 표준적인 버그)가 정답과
한 번도 갈리지 않았다. 랜덤 격자 20만 개를 대조해도 0건이었다.

그래서 P08을 **꺼내는 횟수가 답에 직접 반영되도록** 다시 설계했다. 거리 합을 pop할
때마다 누적하면 중복만큼 합이 커진다.

이건 문제 설계의 일반 원칙이 된다. **드릴이 노리는 실수를 실제로 드러내려면, 문제
쪽에서 그 차이를 관측 가능하게 만들어야 한다.** 실수 이름을 붙여두는 것만으로는
그 실수를 측정하지 못한다.

부수적으로 `curriculum/mistakes.yaml`의 `VISITED_TIMING` 설명을 읽는 방법도 정해졌다 —
"탐색량이 불어난다"가 주 증상이고, 답이 틀리는 것은 문제 형태에 달렸다.

## 함께 확정한 것

**자동 드릴에는 착지점이 있어야 한다**

`auto_drill: true`인 Mistake는 그 `target_skill`을 PRIMARY로 갖는 `MICRO_DRILL` 문제가
반드시 하나 이상 있어야 한다. 없으면 Decision Engine이 `MICRO_DRILL`을 고르고도 줄
문제가 없다. 런타임에는 "다음 행동이 없음"으로 나타나며 원인이 데이터에 있다는 것을
알기 어렵다. CI가 이 짝을 검사한다.

**모든 활성 Skill에는 문제가 있어야 한다**

`skills.yaml`에 있는데 어떤 문제도 다루지 않는 Skill은 영원히 평가되지 않는다.

## 결과

**얻는 것**

- Test Case 집합이 비어 있거나 무력한 상태를 CI가 막는다
- `wrong.py`가 그 문제의 "자주 나오는 실수" 문서 역할을 겸한다. 나중에 Reviewer 평가
  데이터셋의 씨앗으로 쓸 수 있다 — 라벨이 이미 붙어 있는 오답 코드다
- 문제를 추가할 때 "이 문제는 무엇을 걸러내는가"를 강제로 생각하게 된다

**치르는 비용**

- 문제마다 파일이 하나 더 늘고, 그것도 유지해야 한다
- 검증에 Docker가 필요해 CI가 몇 분 더 걸린다. 그래서 참조 무결성 검사
  (`check_problems.py`, Docker 불필요, 1초 미만)와 채점 검증
  (`verify_problems.py`, Docker 필요)을 두 단계로 나눴다
- `wrong.py`가 실제로 갈리는지 확인하는 데 손이 든다. P08은 랜덤 탐색까지 필요했다

## 한계

**`expectedOutput`이 reference에서 나온다.** reference가 틀리면 정답표도 함께 틀리고,
그 상태로도 이 검사는 전부 통과한다. Addendum §65가 요구하는 독립 검증 풀이
(Independent Solver)가 있어야 닫히는 구멍이다. 지금은 SAMPLE case의 기대값을 손으로
쓰고 reference와 대조하는 정도로만 막고 있다 — 슬라이스 1 이후 과제로 남긴다.
