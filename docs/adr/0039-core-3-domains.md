# ADR-0039 · CORE-3 - 이분 탐색 · 그리디 · 수학 · 그래프 · DFS · 트리 · DP · 상태 공간

- 상태: 채택
- 날짜: 2026-09-26
- 정본 근거: PRD §20~22 · §26 · §28 · §33~34 · §37(도메인별 Skill 목록), §126(CORE 취업 코테 필수),
  [ADR-0033](0033-an-accepted-answer-does-not-prove-the-skill.md), [ADR-0034](0034-the-road-to-the-full-prd.md),
  [ADR-0036](0036-core-1-domains.md), [ADR-0037](0037-core-2-domains.md)

## 결정

### 1. Skill 열둘 - CORE 가 여기서 닫힌다

| 도메인 | Skill | needs_skill_control |
| --- | --- | --- |
| BINARY_SEARCH | BINARY_SEARCH_BOUNDS · PARAMETRIC_SEARCH | true · true |
| GREEDY | GREEDY_CHOICE | true |
| MATH | MATH_GCD_LCM · NUMBER_BASE_CONVERSION | true · false |
| GRAPH | GRAPH_REPRESENTATION | true |
| DFS | DFS_TRAVERSAL · GRAPH_CYCLE_DETECTION | false · false |
| TREE | TREE_TRAVERSAL | false |
| DP | DP_1D · DP_2D | true · true |
| STATE_SPACE | STATE_SPACE_BFS | false |

이것으로 PRD §126 의 CORE 목록(Programming ~ Basic Tree)이 전부 켜진다. JOB 트랙(일반 취업 코테)의
범위가 여기서 닫힌다 - 이후 웨이브는 TOP_TIER · ALGORITHM 트랙만 넓힌다.

DFS 는 "DFS 여야 나오는 결과"(진입 · 종료 순서, 번호가 작은 이웃부터 들어갔을 때의 첫 경로)로 정의했다.
연결 요소처럼 BFS 로도 같은 답이 나오는 문제로는 DFS 를 잴 수 없다.

### 2. 생성기는 앞서 만든 초안을 다음 초안에게 보여 준다

CORE-1 · CORE-2 에서 채택된 문제 중 여덟이 같은 Skill 앞 초안과 같은 문제라 철회됐다. 같은 프롬프트로
둘을 만들었기 때문이다. 이번 실행부터 생성기는 한 실행에서 앞서 만든 초안을 "이미 있는 문제" 목록에
붙인다(`DraftPrompt.withDrafts`).

```
CORE-1  채택 20 → 의미 중복으로 철회 5
CORE-2  채택 14 → 의미 중복으로 철회 4
CORE-3  채택 21 → 의미 중복으로 철회 0
```

### 3. 진단 테스트는 기대값을 커리큘럼에서 구한다

"첫 질문은 BFS_SHORTEST_PATH" 처럼 이름을 박아 둔 테스트가 도메인이 늘 때마다 깨졌다(이번에는 그 위에
STATE_SPACE_BFS 가 생겼다). 규칙("선수를 가장 많이 거느린 것부터", "틀린 갈래의 선수로 내려간다")을
커리큘럼에서 다시 계산해 기대값으로 쓴다.

그리고 **"틀린 갈래로 내려간다" 를 실제로 가르는 테스트가 없었다.** 가장 큰 갈래의 꼭대기에서 틀리면
규칙이 없어도 가장 많이 밝혀 주는 것이 그 갈래 안에 있어 통과한다 - 규칙을 빼는 대조군이 실제로
통과했다. 작은 갈래(조합 → 완전 탐색)에서 틀리는 테스트를 더했고, 규칙을 빼면 실패한다.

### 4. 검증 에이전트 검토에서 고친 것

스스로 점검한 뒤에도 검증 에이전트가 실제 채점으로 여섯 가지를 찾았다. 전부 재현한 뒤 고쳤다.

| 문제 | 찾은 것 | 고친 것 |
| --- | --- | --- |
| P65 | "차수가 더 큰 이웃 수" 는 간선마다 나눠 셀 수 있어 인접 리스트 없이 간선 목록 한 번으로 AC | **철회.** 두 정점의 이웃을 맞대야 하는 P77(공통 이웃 세기)을 손으로 썼다. 간선 목록 풀이 · 간선 집합으로 모든 정점을 보는 풀이 모두 TIME_LIMIT |
| P55 · P56 | 질의를 모아 정렬한 뒤 두 포인터로 훑는 오프라인 풀이가 이분 탐색 없이 AC | 질의를 직전 답과 xor 해서 준다 - 앞 답을 알아야 다음 질의가 풀린다. 값은 0 이상으로 옮겼다. P55 의 큰 case 는 √N 블록 풀이가 1.6 초로 통과해 제약 끝(N 200000, Q 100000)으로 키웠다 |
| P72 | 처리량으로 시각을 어림한 뒤 완료 사건을 힙으로 몇 개만 진행하는 풀이가 매개 변수 탐색 없이 AC | 문제는 두고 아래 "남는 위험" 에 적었다 |
| P57 | N 100000 에서 정답 출력이 1MB 를 넘음 | N ≤ 80000(최악 약 94 만 바이트). 제약 끝의 큰 case 를 더했다 |
| P73 | 큰 case 가 없어 벽 조합을 전부 시도하는 풀이가 AC | 200 × 200 · K = 5 case 둘. 조합 풀이는 TIME_LIMIT |
| P74 | 가장 가까운 열쇠부터 줍는 그리디가 AC | 반례 `aS.bBT`(그리디 6, 정답 4)를 더했다 |
| P63 · P64 · P75 | DFS_TRAVERSAL 을 SECONDARY 로 붙였지만 진입 차수 · union-find · BFS 로 풀림 | DFS_TRAVERSAL 을 뗐다. 사이클 판정 Skill 정의에서도 방법(방문 상태 셋)을 뺐다 |
| 개념 자료 | NUMBER_BASE_CONVERSION 예시가 `str(d)` 라 10 이상의 자릿값을 두 글자로 씀 | `DIGITS[d]` |

참고 사항으로 받은 것 가운데 다음도 고쳤다.

| 대상 | 찾은 것 | 고친 것 |
| --- | --- | --- |
| P58 · P63 · P64 · P75 | 큰 case 가 없어(입력 69 바이트 이하) P75 는 조상을 한 칸씩 올라가는 O(N·Q) 도 AC | 제약 끝 case. P75 는 길이 10 만의 사슬을 넣어 올라가기 풀이가 TIME_LIMIT |
| P68 | 큰 case(N 50000)의 답이 0 | N 200000, 답이 0 이 아닌 case |
| P71 | 다시 조립하는 단계를 빼먹은 오답을 OUTPUT_FORMAT("알고리즘은 맞으나")으로 라벨 | IMPLEMENTATION_MISC. 평가 라벨(ADR-0016)이 되므로 맞아야 한다 |
| DiagnosticTest | 기대값이 선수를 트랙 안에서만 셈 - 운영 코드는 거르지 않는다. Evidence 0 을 보는 루프는 대상을 못 찾으면 아무것도 단언하지 않음 | 운영과 같은 식으로 센다. 대상을 찾았는지부터 단언한다 |

두 번째 검토에서 둘이 더 나왔다.

| 문제 | 찾은 것 | 고친 것 |
| --- | --- | --- |
| P55 · P56 | 값의 상위 비트마다 "그 값 이상이 처음 나오는 위치" 를 적어 두고 그 칸에서 몇 칸 훑는 풀이가 이분 탐색 없이 AC - 큰 case 의 값이 고르게 퍼져 칸마다 원소가 적었다 | 폭과 밀도가 제각각인 값 군집(같은 값이 수십 번 겹치는 것까지)에 질의를 몰아 준 case. 칸 크기를 2^8 · 2^10 · 2^14 로 바꾼 풀이 모두 TIME_LIMIT. 질의의 3 할은 군집 밖이라 정수를 하나씩 올라가기만 하는 풀이도 통하지 않는다 |
| P77 | 같은 두 중심 정점을 되풀이해 묻는 제약 안 입력에서 정답이 TIME_LIMIT | 같은 쌍은 두 번 묻지 않는다는 제약과 M ≤ 100000. 정답에 가장 비싼 모양(중심 142 개의 서로 다른 쌍 1 만 개)을 case 로 넣었다 - 638ms |
| P75 | 정답이 1044~1100ms, 보통의 올바른 풀이가 1380ms - 제한 2 초 대비 여유가 얇음 | N ≤ 100000, Q ≤ 100000. 정답 336ms, 보통 풀이 563ms |

P65 의 교훈은 대조 풀이가 "가장 느린 다른 풀이" 였다는 것이다. 채택 검사의 Skill 측정은 대조 풀이
하나가 느린지만 본다 - 그 Skill 없이 **효율적으로** 푸는 길이 있는지는 보지 못한다. 그 길을 찾는 것은
지금은 검증 에이전트의 몫이다.

## 남는 위험

- **그리디는 채점으로 가르기 어렵다.** 대조 풀이(모든 조합)는 걸리지만, 그리디가 아닌 다항 시간 풀이(예:
  구간 DP)도 통과한다. PRD §21 이 "정답만 맞았다고 Greedy 숙련으로 판정하지 않는다" 고 적은 이유이고,
  확인 질문(Explain Back, §148)이 붙기 전까지 GREEDY_CHOICE 의 Evidence 는 "최적해를 효율적으로 구했다" 까지만
  말한다
- **P72 는 매개 변수 탐색 없이도 효율적으로 풀린다.** 처리량 합으로 답을 어림하면 그 시각의 완성 개수가
  M 과 기계 수 N 이내로 차이 나므로, 사건 N 개 정도를 힙으로 진행하면 답이 나온다. case 로 막을 수 없는
  다른 풀이라 GREEDY 와 같이 둔다 - PARAMETRIC_SEARCH 의 Evidence 는 "최소 시각을 효율적으로 구했다" 까지만
  말한다
- **P55 · P56 은 값 칸 표를 섞은 풀이로도 풀린다.** 칸(2^10)마다 위치를 적어 두고, 칸 안 원소가 적으면
  훑고 많으면 값을 하나씩 내려가며 사전에서 찾는 풀이가 반으로 좁히는 단계 없이 AC 다(세 번째 검토,
  제한의 60% 사용). 칸 크기 · 임계값 · 내려가는 범위를 입력에 맞춰 조율한 것이라 이분 탐색을 모르는
  학습자가 자연스럽게 가는 길로 보지 않고, 막으려는 case 를 더 쌓지 않는다. BINARY_SEARCH_BOUNDS 의
  Evidence 는 "정렬된 수열에서 경계 위치를 효율적으로 찾았다" 까지만 말한다
- 정의상 받아들이는 풀이: `bisect` 는 이분 탐색이다(P55 · P56). 값 칸을 여러 단으로 나눠 내려가는 구조(비트 트라이)는 시도하지 않았다 - 칸을 반씩 좁히면 이분 탐색이다. 간선을 정렬해 구간으로 이웃을 꺼내는 것도
  인접 리스트다(P77)
- DFS · 사이클 · 트리 · 상태 공간은 대조가 없다. 판단이지 검증이 아니다(ADR-0033). 큰 case 는 제약 끝을
  확인하려고 둔 것이지 풀이의 효율을 가르려는 것이 아니다
- 검증 에이전트 검토는 이 ADR 을 쓴 뒤에 받는다. 결과는 PR 에 남긴다
