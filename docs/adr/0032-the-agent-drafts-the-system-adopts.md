# ADR-0032 · 에이전트가 초안을 만들고, 시스템이 채택한다

- 상태: 채택
- 날짜: 2026-09-15
- 정본 근거: PRD LLM/시스템 경계 표("문제 변형"), PRD §164 Agent 체크리스트

  [ADR-0007](0007-problems-are-verified-by-a-wrong-solution.md),

## 맥락

판단하는 에이전트는 끝까지 돈다 — 무엇을 모르는지 찾고, 다음 행동을 정하고, 복습을
잡는다(ADR-0028, ADR-0030). 그런데 **콘텐츠를 만드는 에이전트는 비어 있었다.** 문제
15개는 전부 사람이 썼고, 도메인 46개 중 켜진 것은 3개다. 이대로면 유형을 넓히는
비용이 전부 사람 손에 걸린다.

PRD 의 경계 표는 LLM 쪽에 "문제 변형" 을 적어 두었다. 이 저장소가 LLM 을 제한한 이유는
"LLM 이 만들면 안 된다" 가 아니라 **"LLM 이 만든 것을 그대로 믿으면 안 된다"** 다(ADR-0001).

## 결정

**LLM 은 초안만 만든다. 초안이 문제가 되는지는 시스템 검사가 정한다.**

```
생성 (Java)     generator/prompts/problem-v1.md + LlmClient -> generated/drafts/
채택 (Python)   tools/adopt_problem.py -> problems/<CODE>/  또는  generated/rejected/
최종            채택된 문제는 PR 로 들어오고 사람이 마지막에 본다
```

오프라인 저작이다. 사용자 요청 중에 만들지 않는다 — 검증에 샌드박스 실행이 여러 번
들고, 검증 안 된 문제가 사용자에게 가면 mastery 가 오염된다.

언어 경계는 ADR-0011 대로다. LLM 호출은 애플리케이션 쪽(Java)에서 기존 `LlmClient` 와
"파일 이름이 버전" 규칙을 그대로 쓰고, 샌드박스 검증은 이미 있는 Python 하네스를 쓴다.
생성기의 명령은 Reviewer 와 **같은 것**을 `application.yml` 앵커로 공유한다 — 따로 적으면
한쪽만 도구 권한이 열린 채로 남는다.

### 기대 출력은 LLM 에게 받지 않는다

초안 계약(`problem-draft.llm.schema.json`)에는 입력만 있다. 기대 출력은 시스템이
reference 를 실행해서 만든다. LLM 이 정답과 "맞게 틀린" 기대값을 함께 적는 경로를
없애기 위해서다.

Skill 비중(`weight`)과 시간 · 메모리 제한도 받지 않는다. `weight` 는 원래 LLM 요청 스키마의
금지 필드다(`check_curriculum.py`).

### 그러면 reference 가 통과하는 것은 아무것도 증명하지 못한다 — 교차 검증

기대 출력이 reference 에서 나오므로 "reference 가 ACCEPTED" 는 자기 답과 자기를 비교한
것이다. 지금까지의 하네스(`verify_problems.py`)는 사람이 기대값을 따로 쓴다는 전제에서
충분했지만, **생성에서는 정답과 기대값이 함께 틀린 경우를 잡지 못한다.**

그래서 초안은 풀이를 **둘** 낸다 — `reference` 와, 다른 방식으로 쓴 `bruteForce`. 입력
생성기로 무작위 입력 30개를 만들고, 샘플 · 경계 입력과 합쳐 **전부에서 두 풀이의 답이
같아야** 채택한다. 하나라도 갈리면 입력과 두 답을 적어 거절한다.

이것도 증명은 아니다. 같은 모델이 같은 방향으로 틀릴 수 있다. 그래서 bruteForce 는
"다른 방식" 을 요구하고, 채택된 문제도 PR 에서 사람이 본다.

### 채택 검사는 순서대로, 제 단계에서 막는다

```
계약 → 참조 → 중복 → 입력 생성기 → 교차 검증 → 문제 데이터 검사 → 실제 채점
```

> 이후 교차 검증 뒤에 **Skill 측정** 단계가 들어갔다([ADR-0033](0033-an-accepted-answer-does-not-prove-the-skill.md)).

뒤의 두 단계는 **사람이 쓴 문제에 쓰던 검사를 그대로** 쓴다 — 힌트 사다리와 정답 코드
유출(ADR-0026), 오답이 의도한 이유로 실패하는가(ADR-0007). 새로 짜지 않고 문지기로
재사용한다.

`tools/meta_test_adoption.py` 가 검증된 고정 초안을 일부러 망가뜨려 **각 결함이 기대한
단계에서** 막히는지 본다. 엉뚱한 검사에 걸려도 거절은 거절이라, 단계를 보지 않으면
아무것도 거르지 않는 검사가 통과한다. 모델을 부르지 않으므로 CI 에서 돈다.

초안 코드는 **신뢰할 수 없는 입력**이다. 입력 생성기까지 전부 샌드박스에서 돈다.

### 거절도 남긴다

거절된 초안은 단계와 사유와 함께 `generated/rejected/` 에 남는다. 어느 프롬프트 버전이
어떤 이유로 실패하는지가 쌓인다 — Reviewer 정확도를 라벨된 오답으로 재는 것과 같은
방식이다(ADR-0016). 채택률에 기준선을 두지 않는다.

## 파일럿 결과

문제가 하나뿐이던 Skill 4개(`PYTHON_LIST_BASIC` · `PYTHON_DEQUE_BASIC` · `GRID_COORDINATE` ·
`BFS_BASIC`)에 Skill 마다 초안 2개씩, 실제 Claude CLI 로 만들었다(`problem-v1`).

```
초안            8
계약 통과       8
채택            4   P16 BFS 방문 순서 · P17 좌표와 번호 변환 · P18 deque 이동합 · P19 행 · 열 교환
거절            4
```

| 거절 단계 | 사유 |
| --- | --- |
| 중복 | 같은 Skill 의 두 번째 초안이 첫 번째와 같은 code 이름을 냈다 |
| 교차 검증 | 정답이 무작위 입력 4개에서 아무것도 출력하지 않았다 |
| 실제 채점 | 오답이 `RUNTIME_ERROR` 로 틀린다고 적었는데 실제로는 `WRONG_ANSWER` 였다 |
| **사람 검토** | **채택 검사를 통과했지만 P17 과 같은 문제였다** |

**마지막 줄이 이 결정의 가장 중요한 근거다.** 좌표 ↔ 행 우선 번호 변환을 문장만 다르게
쓴 초안이라 본문 글자 유사도(0.75 미만)로는 중복이 아니었고, 샘플 기대 출력까지
`6 / 1 1 / 11` 로 같았다. 기계 검사는 "진짜 문제인가" 는 가려도 **"이미 있는 문제인가"
를 뜻으로는 가리지 못한다.** 채택된 문제가 PR 로 들어오고 사람이 마지막에 보는 단계를
빼지 않는 이유가 실측으로 확인됐다. 이 초안은 단계 `사람 검토` 로 거절 기록에 남겼다.

거절 사유가 한 곳에 몰리지 않은 것도 기록해 둔다 — 네 개가 서로 다른 네 단계에서 막혔다.
단계를 나눠 둔 것이 "왜 버렸는가" 를 말해 준다.

채택률에 기준선을 두지 않는다. 다음 프롬프트 버전은 같은 Skill 로 다시 재서 비교한다.

### 철회: P18 deque 이동합

PR 검토에서 **P18 이 `PYTHON_DEQUE_BASIC` 을 재지 못한다**는 지적이 나왔고, 실제 채점으로
확인했다 - K 칸 전 값을 인덱스로 빼는 풀이가 `ACCEPTED` 였다. 채택 검사 전 단계를 통과한
문제였다. 사람이 쓴 P01 도 같은 결함이 있었다.

P18 을 철회해 단계 `Skill 측정` 으로 거절 기록에 남겼고, 그 단계를 채택 검사에 더했다
([ADR-0033](0033-an-accepted-answer-does-not-prove-the-skill.md)). 사람 검토가 기계 검사가
못 본 것을 찾은 두 번째 사례다 - 이번에는 **"같은 문제인가" 가 아니라 "그 Skill 을 재는가"** 였다.

새 단계로 deque 초안 2개를 다시 만들었고 채택은 0이다. 하나는 새 단계에서 막혔고, 하나는
통과했지만 정렬 지름길이 있어 사람 검토에서 거절했다(ADR-0033 결과).

## 남는 위험

- **의미상 중복을 기계가 잡지 못한다.** 파일럿에서 실제로 났다(위 표). 본문 글자
  유사도는 문장을 바꿔 쓴 같은 문제를 통과시킨다
- **교차 검증은 같은 모델의 같은 착각을 못 잡는다.** 두 풀이가 같은 오해에서 출발하면
  같은 틀린 답을 낸다. 사람의 PR 검토를 빼지 않는 이유다
- **완전탐색으로 검증하기 어려운 유형**(큰 입력에서만 의미가 갈리는 최적화)은 작은 무작위
  입력으로 드러나지 않을 수 있다. 새 도메인으로 넘어갈 때 다시 본다
- **생성된 문제는 `probes` 태그를 달지 않는다.** 태그를 달려면 경쟁 실수 전부의 오답이
  필요한데(ADR-0015), 그것까지 생성하면 검증 비용이 크게 는다. 그래서 이 문제들에서
  Reviewer 확정은 §21-A 가 아니라 §21-B(재발)로만 난다
- 실서비스 문제은행(`CURATED`)은 공개 저장소에 두지 않는다(ADR-0008). 파일럿 문제는 전부
  `DEV_FIXTURE` 다
- 모델 호출 비용과 시간은 로컬 Claude CLI 세션에서 나간다
