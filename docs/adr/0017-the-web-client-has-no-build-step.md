# ADR-0017 · 화면은 빌드 도구 없이 두고, API 를 소비만 한다

- 상태: 채택
- 날짜: 2026-09-06
- 정본 근거: [ADR-0001](0001-llm-analyzes-system-decides.md), [ADR-0002](0002-next-action-decided-by-rule-engine.md), [ADR-0013](0013-judging-happens-outside-the-request.md)

## 맥락

슬라이스 1 은 **수직 슬라이스**인데 화면이 없었다. 제출 → 채점 → Evidence → mastery →
다음 행동까지 전부 도는데, 그것을 사람이 확인할 방법이 `curl` 과 `psql` 뿐이었다.

## 결정

**빌드 도구를 두지 않는다.** `index.html` · `app.js` · `app.css` 세 파일을 Spring 이
정적 자원으로 그대로 서빙한다.

npm · 번들러 · 프레임워크를 들이면 저장소에 **두 번째 빌드 파이프라인**이 생긴다.
지금 화면은 목록 · 문제 · 제출 · 결과 네 덩어리이고, 그 비용을 정당화하지 못한다.
화면이 커져서 상태 관리가 필요해지면 그때 도입한다 — 그때는 이 ADR 을 갈음한다.

### 화면은 판단하지 않는다

판정 · mastery · 다음 행동은 전부 서버가 정해서 내려준다(ADR-0001, ADR-0002).
화면은 그것을 **보여주기만** 한다.

이 경계는 서버 쪽에서 스키마로 강제하고 있는데(LLM 출력에 `score`/`nextAction` 이
못 들어온다), 화면 쪽에도 같은 틈이 있다. 점수를 화면에서 계산하기 시작하면 서버가
정한 것과 화면이 보여주는 것이 갈리고, **사용자가 보는 쪽이 이긴다.**

그래서 `WebClientTest` 가 `app.js` 에서 `mastery` · `MICRO_DRILL` · `CONFIRMED`
같은 것을 다루는 코드를 찾으면 실패시킨다. 주석은 뺀다 — 규칙은 코드에 대한 것이다.

### 빌드가 없으면 타입 검사도 없다

없는 엔드포인트를 불러도 눌러 보기 전에는 아무도 모른다. 그래서 화면이 부르는
**method 와 경로**를 실제 매핑과 대조한다. 경로만 보면 부족하다 — `/api/users` 는
POST 만 있는데 GET 으로 불러도 경로는 맞으므로 통과하고, 눌러 보면 405 다.
프레임워크 없이 얻을 수 있는 검사 중 값이 가장 크다.

`index.html` 이 참조하는 정적 파일이 실제로 서빙되는지도 같이 본다.

## 실제로 띄워 보고 알게 된 것

**두 가지는 화면을 만들기 전에는 드러나지 않았다.**

**1. 새 DB 에서는 아무것도 시작할 수 없었다.** 인증이 없어 화면이 `userId` 를 직접
보내는데, 그 id 를 만들 방법이 없었다. `POST /api/users` 를 뒀다 — 계정이 아니라
**학습 이력을 매달 자리**다. 비밀번호도 세션도 없고, 인증이 붙으면 사라진다.

**2. 문제 목록 순서가 실행마다 달랐다.** `ProblemCatalog` 이 `Map.copyOf` 로 담아
순서를 잃는다. 같은 데이터인데 화면이 다르게 보이므로 `code` 순으로 고정했다.

## 문제 목록은 학습 경로가 아니다

`GET /api/problems` 는 **첫 제출 이전의 진입점**이다. 제출이 하나도 없으면 무엇을
줄지 정할 근거 자체가 없다(ADR-0002 의 Decision Engine 은 판정을 입력으로 받는다).

그 뒤로는 화면이 목록을 다시 쓰지 않는다. `다음 문제로` 는 `next-problem` 이
가리키는 것을 연다 — **무엇을 풀지 고르는 것은 사용자가 아니라 시스템이다.**

## 채점을 기다리는 방식

채점은 요청 안에서 끝나지 않으므로(ADR-0013) 제출 뒤에는 폴링한다.

**한도를 두고 포기하지 않는다.** 처음에는 2분 한도를 두고 넘으면 멈췄는데, 서버는
그보다 훨씬 오래 걸릴 수 있다 — 재시도까지 세면 최악이 14분쯤 된다(Worker 의
`WORKER_TIMEOUT_SECONDS` × `MAX_ATTEMPTS` + backoff + Reviewer timeout).

그 숫자를 화면에 옮겨 적는 것도 답이 아니다. **UI 가 Worker 내부값에 묶이고**, 그
값이 바뀔 때마다 또 갈린다. job 은 큐에 살아 있는데 화면이 임의의 시간 때문에 관찰을
포기할 이유가 없다.

그래서 2분이 지나면 **오래 걸린다고 말해 주고 폴링 간격을 1초에서 5초로 늘린다.**
기다리는 것과 방치하는 것은 다르다 — 조용히 멈추면 사용자는 화면이 죽은 것인지
채점이 느린 것인지 알 수 없고, 계속 1초마다 때리면 그것대로 낭비다.

Worker 를 띄우지 않고 제출한 뒤 뒤늦게 띄워 봤다. 경고가 뜬 채 폴링이 이어지고,
Worker 가 올라오자 결과가 그대로 도착했다.

## 결과

- 수직 슬라이스를 사람이 눌러서 확인할 수 있다. 제출 → 판정 → 분석 → 다음 행동 →
  다음 문제까지 한 화면에서 돈다.
- **인증이 없다는 것이 이제 눈에 보인다.** 화면에 사용자 id 입력란이 있고, 아무 값이나
  넣을 수 있다. 이 저장소는 배포하지 않으며 만든 사람이 자기 PC 에서 돌린다는 전제
  위에 있다 — 그 전제가 깨지는 날 이 입력란이 가장 먼저 사라진다.
- 화면 코드에는 테스트가 없다. 검사하는 것은 **경계**(부르는 API, 판단하지 않음)이지
  화면 동작이 아니다. 브라우저를 띄우는 테스트는 지금 비용이 값보다 크다.
