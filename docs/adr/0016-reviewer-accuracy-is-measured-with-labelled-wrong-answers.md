# ADR-0016 · Reviewer 정확도는 라벨된 오답으로 재고, CI 에 넣지 않는다

- 상태: 채택
- 날짜: 2026-09-06
- 정본 근거: PRD §135 / [ADR-0014](0014-reviewer-output-is-a-claim-until-judge-evidence-agrees.md) / [ADR-0015](0015-failure-shape-is-the-independent-evidence.md)

## 맥락

지금까지 Reviewer 를 다루는 규칙을 여럿 만들었다 — 검증에서 떨어뜨리고, confidence
구간으로 나누고, 실패의 모양으로 뒷받침하고, 재발을 센다. 전부 **"이 분석을 어디까지
믿을 것인가"** 에 대한 답이다.

그런데 정작 **얼마나 맞히는지는 한 번도 재지 않았다.** 규칙의 보수성이 적절한지
말할 근거가 없다는 뜻이다. §21-A 를 열면서 "오분류가 곧바로 학습 경로 오염" 이라고
적었지만, 그 오분류가 얼마나 자주 일어나는지는 아무도 모른다.

정확도를 재려면 정답지가 필요하다. 사람이 라벨을 붙이는 것이 보통이지만, 이 저장소에는
**이미 정답지가 있다.**

```text
wrong.py              problem.yaml 의 negativeControl.mistake   (ADR-0007)
probes/<MISTAKE>.py   파일 이름이 곧 라벨                        (ADR-0015)
```

그리고 이 라벨들은 주석에만 적힌 주장이 아니다. CI 가 **실제로 채점해서** 그 실수가
의도한 판정을 내는지, 태그된 case 를 실패시키는지, 다른 실수와 구별되는지 확인한다.

## 결정

**저장소의 라벨된 오답으로 Reviewer 정확도를 잰다.**

```text
tools/gen_reviewer_eval_cases.py --write    라벨 + 실제 채점 결과를 묶어 둔다 (Docker)
ReviewerEvaluation (main)                   진짜 모델을 부르고 라벨과 대조한다 (Claude CLI)
```

두 단계로 나눈 이유는 한 프로세스가 둘을 동시에 갖추기 어렵기 때문이다 — 채점은
Docker 가, 모델 호출은 로그인된 CLI 가 필요하다. 채점 결과를 고정해 두면 평가를
반복해도 채점은 한 번이면 된다.

고정한 것은 **손으로 적은 기대값이 아니라 실제 채점 결과**다. `--write` 없이 돌리면
지금 파일이 실제 채점과 같은지 검증한다 — golden fixture 와 같은 규율이다(ADR-0010).

### 라벨 주석은 지우고 보낸다

오답 파일 첫머리에는 무엇을 틀리게 했는지 적혀 있다. 그대로 보내면 모델은 분석하지
않고 읽기만 하면 된다 — **정확도가 아니라 독해력을 재게 된다.** 생성기가 첫 주석
블록을 지운다.

### 실패 case 의 입력은 평가 케이스에 복사하지 않는다

모델에게 주는 나머지 입력은 실제 경로와 **같은 곳에서** 읽는다(`ProblemCatalog`).
복사해 두면 정답표가 `tests/` 에 한 벌 더 생기고, 더 나쁘게는 모델이 받는 것이
production 과 달라져 여기서 잰 정확도가 실제와 무관해진다.

## CI 에 넣지 않는다

모델 호출은 느리고 비결정적이다. CI 에 넣으면 **모델이 그날 다르게 답했다는 이유로
관계없는 PR 이 빨개진다.** 그리고 이 저장소는 API 키를 받지 않는다 — 로컬 CLI 의
로그인 세션을 쓰므로 CI 에는 부를 방법 자체가 없다.

대신 평가 케이스가 **실제 채점과 일치하는지**는 CI 가 본다. 그쪽은 결정론적이다.

## 단언은 하나뿐이다

정확도에 임의의 기준선을 두지 않는다. "70% 이상" 같은 숫자는 근거가 없고, **근거 없는
기준을 통과했다고 안심하는 편이 재지 않는 것보다 나쁘다.**

대신 **오확정 0건**만 단언한다 — 라벨과 다른 Mistake 가 `CONFIRMED` 까지 가는 것.
§21-A 가 서 있는 전제이기 때문이다. 그 사용자는 자기가 하지 않은 실수의 드릴을 받는다.

나머지(일치율, 검증 탈락률, 혼동 행렬)는 **보고만 한다.** 숫자가 나쁘면 프롬프트를
고치거나 확정 조건을 조이는 근거가 되지, 그 자체로 빌드를 깨뜨릴 일은 아니다.

## 첫 측정 (reviewer-v1, 20건)

```text
쓸 수 있는 분석   20/20     검증에서 떨어진 것 없음
primary 일치      17/20
한 번의 분석만으로 확정(§21-A)   4건 — 전부 라벨과 일치
오확정            0건
```

불일치 3건 중 **2건은 모델이 아니라 라벨이 틀렸다.** `INDEX_ERROR` 로 라벨한 풀이가
격자를 **읽을 때** 행/열을 뒤바꾸고 있었다 — 그건 `INPUT_PARSE`("입력 형식을 잘못
읽는다")다. 모델은 두 번 다 `INPUT_PARSE` 라고 답했고, 그게 맞다.

참조 시점에 뒤바꾸도록 고쳐 라벨을 명확히 한 뒤 그 3건만 다시 돌렸더니 3/3 이 됐다.
합치면 19/20 이다. **하네스가 처음 한 일이 우리 데이터의 오류를 잡은 것이다.**

남은 불일치 1건은 실제 오분류다 — `P01_QUEUE_BASIC` 의 `OUTPUT_FORMAT` 을
`BOUNDARY_CHECK`(0.90)로 봤다. 큐 문제에 경계 검사는 없다. 확정되지 않은 이유는
P01 에 `probes` 태그가 없어서다 — **뒷받침 조건이 실제로 오확정을 막았다.**
태그가 있었다면 이 건은 CONFIRMED 로 갔을 수 있다.

⚠️ 이 결과를 보고 프롬프트를 고치지 않았다. 고친 것은 라벨이고, 라벨이 taxonomy 와
어긋난 것은 프롬프트와 무관하게 잘못이다.

## 이 하네스가 재지 않는 것

- **§21-B(재발)** — 사용자 이력이 필요하다. 여기서 재는 것은 한 번의 분석만으로
  확정까지 가는 경로, 즉 §21-A 다.
- **실제 사용자의 오답** — 평가 집합은 우리가 심은 실수다. 사람의 오답은 여러 실수가
  겹치고, 어느 것이 "그" 원인인지 애매하다. `mistake_detections` 에 쌓이는 라벨이
  그 자리를 채워야 한다.
- **정확도의 개선** — 이 파일을 보고 프롬프트를 고치면 평가 집합에만 맞춘 프롬프트가
  된다. 프롬프트를 바꿀 때는 파일 이름을 새로 만들고(§PRD 135), 두 버전을 같은
  집합으로 재서 비교한다.

## 결과

- 프롬프트를 바꿀 근거가 생겼다. `promptVersion` 별로 같은 집합을 돌려 비교한다.
- 평가 집합은 문제를 추가할 때 함께 늘어난다. `probes/` 에 오답을 하나 넣으면
  평가 케이스가 하나 는다 — 따로 관리하는 정답지가 아니다.
- 라벨이 편향돼 있다. 슬라이스 1 의 오답은 대부분 우리가 한 줄 고쳐 만든 것이라
  실제 사용자 코드보다 깨끗하다. **여기서 잰 정확도는 상한에 가깝다.**
