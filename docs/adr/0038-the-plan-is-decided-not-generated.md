# ADR-0038 · 오늘의 계획은 생성하지 않고 결정한다

- 상태: 채택
- 날짜: 2026-09-26
- 정본 근거: PRD §80(Daily Planner), §81(학습 우선순위), §82(시험 직전 모드), §83(Learning ROI),
  §115(API — Daily Plan), §121(Dashboard), §122(Skill Map UI), §123(오답 분석 UI), §152(사용자 설정),
  [ADR-0001](0001-llm-analyzes-system-decides.md), [ADR-0002](0002-next-action-decided-by-rule-engine.md),
  [ADR-0019](0019-the-diagnostic-is-an-input-to-the-decision-engine.md),
  [ADR-0021](0021-a-review-is-what-the-schedule-says-it-is.md),
  [ADR-0034](0034-the-road-to-the-full-prd.md)

## 맥락

PRD §87 은 Planner 를 "Agent" 로 부른다. 그런데 계획이 하는 일은 "오늘 무엇을 얼마나 할지" 를
정하는 것 - 다음 행동과 같은 종류의 **결정**이다. 이 저장소는 결정을 LLM 에게 묻지 않는다(ADR-0001).

## 결정

### 1. 계획은 순수 함수가 정한다

`DailyPlanner` 는 입력(Skill 상태 · 만기 복습 · 진단 중인 Skill · 문제별 예상 시간 · 하루 시간 ·
시험까지 남은 날)만 보고 계획을 낸다. 같은 입력에 같은 계획이다.

순서는 이렇다.

```
진단(아직 묻는 중이면) → 만기 복습 → 연습 · 새로 배우기를 번갈아 → 남은 시간은 혼합
```

**진단과 만기 복습은 예산과 상관없이 넣는다.** 들어가지 않는다고 건너뛰면 그 자리를 우선순위가 낮은
블록이 채운다 - 하루 10 분인 새 사용자에게 진단(20 분) 대신 짧은 새 Skill 이 나와 계획과 결과 패널이
다른 곳을 가리켰다(검증 에이전트가 재현). 혼합 블록은 20 분까지이고(PRD 예시 10~20 분), 남는 시간은
"줄 문제가 없어 비워 둔다" 고 말한다 - 새 사용자에게 720 분 중 691 분이 갈 곳 없는 혼합이었다.

진단이 맨 앞인 이유는 ADR-0019 다 - 진단 중에는 다음 행동도 진단을 가리킨다. 계획과 결과 패널이
다른 곳을 가리키면 사용자는 어느 쪽을 따를지 모른다. API 테스트가 두 곳이 같은 문제인지 본다.

### 2. §81 의 여섯 항 중 잴 수 있는 것만 쓴다

| 항 | 쓰는가 | 무엇으로 |
| --- | --- | --- |
| GoalImportance | 쓴다 | 트랙 안인가(ADR-0035) |
| Weakness | 쓴다 | `1 - mastery` |
| Learnability | 쓴다 | 선수를 채웠는가(LOCKED 제외) |
| **ExamFrequency** | **쓰지 않는다** | 출제 빈도 데이터가 없다. 어림한 값이 순서를 정하면 근거 없는 숫자가 계획이 된다 |
| RetentionNeed | 쓴다 | 만기 복습을 맨 앞에 |
| EstimatedStudyCost | 쓴다 | 고른 문제의 `expectedSolveSeconds` |

### 3. 시험 7 일 이하면 굳힌다(§82 · §83)

새로 배우지 않고, 연습은 **이미 가까운 것부터**(mastery ÷ 시간) 둔다. 평소에는 약한 것부터다.
단위 테스트가 두 모드에서 첫 블록이 뒤집히는지 대조군으로 본다.

### 4. 모르는 것은 어림하지 않는다

하루 시간을 정하지 않은 사용자에게 60 분 같은 기본값을 쓰지 않는다 - 그러면 정하지 않은 사용자와
60 분을 고른 사용자가 구별되지 않는다(목표에 기본값을 두지 않은 ADR-0035 와 같은 이유). 그때 계획은
시간을 나누지 않고 앞의 세 블록만 순서대로 준다. 설정 API 는 두 키를 모두 받아야 한다 - 생략은
400, null 은 "정하지 않았다" 다. 지난 시험일은 없는 시험이다.

### 5. 문제는 다음 행동과 같은 규칙으로 고른다

계획이 고른 Skill 을 문제로 옮기는 것은 `NextProblemService` 다 - 결과 패널과 같은 규칙이다. 줄 문제가
없는 Skill 은 계획에 넣지 않는다.

### 6. 대시보드는 보여 주기만 한다

- **오늘**(§121): 시험 D-day · 오늘 시간 · 숙달 수 / 트랙 Skill 수 · 할 일 블록. 숫자는 서버가 센다
- **최근 오답**(§123): 최근 제출 50 개에서 PRIMARY 로 탐지된 실수를 센다. 그 문제에서 일어날 수 없다고
  선언된 탐지(ADR-0029)는 세지 않는다 - 확정 규칙이 무시한 주장으로 숫자가 부풀면 안 된다. **확정과 탐지를 나눠
  보여 준다** - 확정되지 않은 분석은 주장일 뿐이다(ADR-0014)
- **Skill 지도**(§122): 도메인으로 묶어 보여 준다. 묶는 것은 표시 방식이고 값은 서버 그대로다

## 결과

- `GET /api/users/{id}/today` · `GET /api/users/{id}/mistakes` · `PUT /api/users/{id}/settings`,
  계약 `today.schema.json` · `mistake-summary.schema.json`, `user.schema.json` 에 설정 두 필드
- 화면에 "오늘" 탭. 늦게 온 이전 사용자의 계획이 지금 화면을 덮지 않는지 e2e 가 게이트로 본다 -
  표 확인을 빼면 실제로 깨진다(대조군)

## 남는 위험

- 계획은 하루 단위 스냅숏이다. 블록 하나를 끝내면 다시 불러야 다음 계획이 갱신된다
- 문제의 예상 시간은 생성 초안이 적은 값이다. 실제 풀이 시간과 다를 수 있다
- 출제 빈도(ExamFrequency)를 쓰지 않으므로 "자주 나오는 유형 먼저" 는 계획에 없다
- 계획은 확정된 실수의 드릴(MICRO_DRILL)을 넣지 않는다. 결과 패널이 드릴을 줄 때 계획은 같은 Skill 의
  일반 문제를 줄 수 있다 - 확정된 실수의 교정은 그 Skill 안의 일이라 결과 패널의 몫으로 둔다
- 만기 복습이 여럿이면 전부 필수로 들어가 하루 시간을 몇 배 넘을 수 있다. 결과 패널은 한 번에 하나만
  보낸다. 넘치면 reason 이 그렇다고 말한다
