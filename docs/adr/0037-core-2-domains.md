- 정본 근거: PRD §13~19(도메인별 Skill 목록), [ADR-0033](0033-an-accepted-answer-does-not-prove-the-skill.md),

## 결정

### 1. Skill 여덟 - 일곱이 needs_skill_control

| 도메인 | Skill | needs_skill_control |
| --- | --- | --- |
| HEAP | HEAP_PRIORITY | true |
| RECURSION | RECURSION_BASIC · DIVIDE_AND_CONQUER | false · true |
| BACKTRACKING | BACKTRACKING | true |
| TWO_POINTER | TWO_POINTER | true |
| SLIDING_WINDOW | SLIDING_WINDOW | true |
| PREFIX_SUM | PREFIX_SUM · DIFFERENCE_ARRAY | true |

이 여섯 도메인은 전부 **"매번 처음부터 다시 하는 풀이도 작은 입력에서는 같은 답"** 인 기법이다.
정답만으로는 그 기법을 썼는지 알 수 없으므로 대조 풀이가 큰 입력에서 걸려야 채택한다(ADR-0033).
재귀 기본만 대조가 없다. 처음에는 "자기 호출로 푼다" 로 정의했지만 채점으로 관측할 수 없었다 -
검증 에이전트가 문자열을 통째로 만드는 풀이 · 끝자리 0 개수 공식 · 비트 공식으로 모두 AC 를 받았다.
그래서 정의를 **재귀적 정의를 읽고 n 단계 결과를 구하는 능력**으로 고쳤다(ADR-0033 §1).

**PREFIX_SUM_2D 는 이번 웨이브에서 올리지 않는다.** 행마다 1 차원 누적 합을 만들고 열 방향 슬라이스
합을 두 번 하는 풀이가, 격자 500×500 · 질의 10 만에서도 988ms 로 통과했다. 더 키우면 정답도 시간
예산에 걸린다 - 파이썬 채점 한도 안에서 2 차원 누적 합을 가를 수 없다. `skills.yaml` 에는 검증된
Skill 만 둔다.

모두 CORE 이고 JOB 트랙 이상에서 켜진다. 입문(INTRO) 트랙은 PRD §129 대로 이 도메인들을 담지 않는다.

### 2. 진단의 함의는 트랙 밖 Evidence 까지 본다

CORE-2 를 더하자 `TrackTest` 가 깨졌다. JOB 으로 진단을 끝낸 사용자가 INTRO 로 바꾸면 **끝난 진단이
다시 열렸다.** BACKTRACKING 을 통과해 함의된 RECURSION_BASIC · COMBINATORIAL_ENUMERATION 이,
BACKTRACKING 이 INTRO 에 없어서 함의에서 사라진 것이다.

ADR-0035 §3-1 과 같은 원칙이다 - **판단은 전체에서, 묻고 보여 주는 것은 트랙 안에서.** 진단은
물을 범위(트랙)와 함의를 구할 상태(전체)를 따로 받는다. 수정 전에 실패하던 그 테스트가 회귀 테스트다.

## 결과

`problem-v2` 로 Skill 마다 초안 2 개.

```
초안 18 · 계약 통과 18 · 채택 검사 통과 14 · 검증 검토 뒤 8 · 손으로 쓴 문제 1 (P76)
```

| 거절 | 단계 | 사유 |
| --- | --- | --- |
| 3 | Skill 측정 | 대조 풀이가 작은 입력에서 이미 틀림(둘) · 정답이 큰 입력에서 OUTPUT_LIMIT(하나) |
| 1 | 중복 | 같은 Skill 둘째 초안이 같은 제목 |
| 4 | 검증 검토 | P45 · P48 · P54 · P52 가 P44 · P47 · P53 · P51 과 같은 문제 |
| 2 | 검증 검토 | P47 - 2 차원 누적 합을 가를 수 없다 · P43 - 공식과 내장 `pow` 로 분할 없이 풀린다(큰 case 도 제약 밖) |

검증 에이전트가 새 문제 11 개 중 7 개를 PRIMARY Skill 없이 풀었다. 대부분 **큰 case 에 다양성이
없었다** - 갱신이 전부 같은 구간(묶어서 더하기), 질의가 열 가지뿐(캐시), 넣기를 몰아서 한 뒤 꺼내기를
몰아서(한 번만 정렬), 모든 값이 1(전부 답이라 공식). 초안의 큰 입력 생성기가 만든 입력이다.

| 문제 | 뚫은 풀이 | 고친 것 |
| --- | --- | --- |
| P42 | 같은 (l, r) 를 묶어 직접 더하기 | 무작위 구간 10 만 개. 묶기 · 대조 모두 TIME_LIMIT |
| P46 | 질의별 캐시 + 슬라이스 합 | 서로 다른 무작위 질의 5 만 개 |
| P44 | 새 값이 있을 때만 정렬하고 끝에서 꺼내기 | 넣기와 꺼내기를 번갈아 |
| P53 | 모든 값이 1 이라 전부 답 | 무작위 값 · S = 500 만 |
| P41 | N=10 에서 막힌 칸 없는 판 하나뿐 - 답을 표로 박아 넣기 | 막힌 칸이 있는 N=10 판 둘 · N=9 판 하나, 중복 case 제거 |
| P43 | 등비수열 공식 + 내장 `pow` | 철회. 내장 함수가 대신할 수 없는 **피보나치 n ≤ 10^18**(P76)을 손으로 썼다 - 두 배 공식, 완전탐색과 307 개 대조, 10^18 은 행렬 거듭제곱으로 따로 대조 |
| P52 | 첫 구간이 이미 최댓값 - 조기 종료 | P51 과 중복이라 철회 |
| P76 | m = 10^9 = 2^9·5^9 라 피사노 주기 + CRT 로 분할 없이 AC. 다음에는 주기 상한 2(p+1) 로 줄인 번호가 3844 뿐이라 선형으로 AC | 5 로 나눠 ±2 인 큰 소수(999999937) m 과, **2(p+1) 로 줄여도 큰 번호가 남는 n**(나머지 7.6억 · 12.2억)의 case 둘. 주기(약 2.86·10^8)를 찾는 풀이도 막히고, 5 가 이차잉여가 아니라 Binet 경로도 막힌다 |

**출력 상한**도 맞췄다. 제약 안의 입력에서 정답이 OUTPUT_LIMIT 을 받았다(P42 · P46 · P51) -
N · Q 를 줄여 최악 출력을 1MB 아래로 뒀다.

**정의상 받아들이는 풀이**: `bisect.insort` 로 정렬을 유지하는 풀이(P44, 넣을 때마다 C 수준에서
옮기지만 10 만 규모에서 힙과 가르려면 입력이 수백만 줄이 된다), 누적 합 + 이분 탐색(P53, O(N log N))은
AC 다. 제곱근 분할(P46, 블록 합 + 슬라이스)도 AC 다 - 누적 합보다 고급 기법이라 받아들인다.

**진단 크래시**: 함의를 전체에서 구하게 고친 첫 수정이, 트랙 밖에서 실패한 Skill 의 선수를 물을 후보로
넣어 후보가 비면 예외로 멈췄다 - 진단 조회도 다음 제출의 반영도 실패해 채점이 끝나지 않았다. 물을
후보는 트랙 안으로 제한하고, 그 흐름을 대조군과 함께 회귀 테스트로 넣었다.

같은 프롬프트로 둘을 만들면 같은 문제가 나오는 것이 CORE-1 에 이어 또 났다. CORE-3 부터 생성기는
앞서 만든 초안을 다음 초안에게 "이미 있는 문제" 로 보여 준다.

## 남는 위험

- 대부분의 Skill 이 문제 하나뿐이다
- P41 의 여유가 얇다. 전체 순열을 최적화해 거르는 풀이가 `--cpus 0.5` 에서 4.1s(제한의 약 2 배)다 -
  채점 기계가 두 배 빠르면 가지치기 없이도 들어올 수 있다
- 초안의 큰 입력 생성기는 다양성이 없는 입력을 만든다. 다음 프롬프트 버전에서 "캐시 · 묶기 · 조기 종료가
  통하지 않게" 를 요구해야 한다 - 이번에는 검증 에이전트가 찾았다
- 백트래킹의 "가지를 잘랐는가" 는 시간으로만 가른다. 가지치기 없이 빠른 다른 풀이(예: 비트마스크
  DP)가 있으면 그것도 통과한다
