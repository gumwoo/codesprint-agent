# ADR-0027 · 힌트 단계는 신고받지 않고 관측한다

- 상태: 채택
- 날짜: 2026-09-13
- 정본 근거: PRD §73 · §74 · §109 · §118, Addendum §22,
  [ADR-0001](0001-llm-analyzes-system-decides.md),
  [ADR-0026](0026-hint-ladder-is-problem-data.md)

## 맥락

[ADR-0026](0026-hint-ladder-is-problem-data.md) 으로 사다리를 데이터로 두었다.
남은 것은 **누가 몇 단계까지 봤는가**이고, 그것이 실제로 mastery 를 가른다.

```
AC_BY_HINT[0] = (0.90, 0.95)
AC_BY_HINT[3] = (0.80, 0.55)   <- independent 가 절반 아래로
AC_BY_HINT[6] = (0.55, 0.10)   <- 해설을 본 경우
```

예전에는 그 숫자를 **제출 요청이 실어 왔다.** 힌트 기능이 없던 시절인데도 받았고,
아무도 확인할 수 없는 값으로 mastery 가 깎였다. PR #19 에서 입력을 막았지만
(0 / false 만 허용), 그것은 구멍을 막은 것이지 채운 것이 아니다.

## 결정

**서버가 힌트를 내주면서 기록하고, 제출은 그 기록에서 읽는다.**

```
POST /api/problems/{code}/hints/{level}   내주고 hint_usage 에 남긴다
POST /api/problems/{code}/submit          그 기록에서 최고 단계를 읽어 제출 행에 얼린다
```

Reviewer 에서 "confidence 는 LLM 이, 확정은 시스템이" 로 그은 선과 같다(ADR-0001).
나중에 LLM 이 힌트 문구를 사용자 코드에 맞춰 다듬어도 이 선은 움직이지 않는다.

### 신고를 무시하지 않고 거절한다

필드를 조용히 지우면 Jackson 이 모르는 값을 버린다. 그러면 **보낸 쪽은 그 값이
적용됐다고 믿는다** — 화면은 "해설을 봤다" 고 보냈는데 기록에는 없어서 독립 풀이로
남는 상태가 가장 나쁘다.

그래서 `hintLevel` / `solutionViewed` 를 `Integer` / `Boolean` 으로 두고 **null 이
아니면 400** 이다. `0 / false` 도 거절한다 — 무해해 보이지만, 받아 주면 나중에 `5` 를
보내도 되는 줄 알게 된다.

### 한 단계씩만 연다

건너뛰기를 허용하면 H1 만 보고 바로 H5 를 열 수 있고, 그때 기록되는 값은 H1~H5 를
차례로 본 사람과 **같은 5** 다. 실제로 받은 도움의 양이 다른데 같은 벌점을 받는다.
사다리는 위로 갈수록 더 주기로 되어 있고(ADR-0026), 그 순서가 지켜져야 숫자 하나가
도움의 양을 대신할 수 있다.

### 본 힌트는 되돌릴 수 없다

제출마다 "이번에 새로 본 힌트" 를 세지 않고 **지금까지의 최댓값**을 쓴다.

H3 를 보고 실패한 뒤 힌트 없이 다시 내도 그 사람은 여전히 H3 를 알고 있다. 두 번째를
"힌트 없는 풀이" 로 세면 독립 풀이를 실제보다 높게 기록한다 — 그리고 그 방향의 오차는
**사용자가 의도적으로 만들 수 있다.** 힌트를 다 보고 나서 제출만 여러 번 하면 된다.

같은 이유로 같은 단계를 다시 열어도 새 기록이 되지 않는다. 그렇지 않으면 여러 번
열어 본 사람이 **더 많이 본 것으로** 계산된다.

### 같은 단계를 두 번 여는 것은 **성공해야 한다**

"다시 열어도 새로 기록하지 않는다" 는 이 서비스가 약속한 성질이다. 그런데 처음에는
`highestLevel()` 을 읽고 새 단계일 때만 `save()` 하는 구조였고, **순차 재요청에서만
지켜지는 약속이었다.**

리뷰에서 지적됐고 재현했다 — 같은 H1 요청 여덟 개를 동시에 보내니 일곱이
`hint_usage_once_per_level` 위반으로 터졌다. 더블클릭 · 재시도 · 응답을 못 받아 다시
누르는 경우에 그대로 일어난다.

```sql
insert into hint_usage (...) values (...)
on conflict (user_id, problem_id, hint_level) do nothing
```

예외를 잡아 넘기지 않는다. 제약 위반이 나면 그 트랜잭션은 이미 rollback-only 라 같은
트랜잭션에서 이어서 읽고 쓸 수 없다. **충돌 자체를 만들지 않는 쪽이 맞다** — 복습
일정이 조건부 UPDATE 를 쓰는 것과 같은 이유다(ADR-0021).

### 읽은 값은 제출 행에 얼린다

Evidence 는 append-only 정본이다(ADR-0009). 제출한 뒤에 H5 를 더 봤다고 이미 낸
제출의 관측이 따라 바뀌면, 같은 제출이 시점에 따라 다른 mastery 를 만든다.

### `POST` 다

내용을 읽는 것처럼 보이지만 서버에 기록이 남는다. `GET` 으로 두면 프리페치나
새로고침이 힌트를 본 것으로 기록한다 — 그리고 그 기록은 지울 수 없다.

## PRD 와 다른 점

PRD §109 의 `hint_usage` 에는 `submission_id` 가 있다. **두지 않았다.**

힌트는 제출보다 먼저 일어나므로 그 시점에 붙일 제출이 없고, 나중에 청구하게 하면
"어느 제출이 이 힌트를 가져갔는가" 라는 상태를 하나 더 관리해야 한다. 그런데 위에
적은 대로 **본 힌트는 되돌릴 수 없으므로 소비 개념 자체가 없다** — 최댓값만 있으면
된다. 복습 일정(ADR-0021)이 청구를 쓰는 것과 다른 이유가 그것이다. 그쪽은 한 번
쓰면 없어진다.

## 결과

- 힌트 의존도 산식(`AC_BY_HINT`)이 처음으로 실재하는 입력을 받는다. 0 말고 다른 값이
  들어오는 길이 열렸다
- 제출 API 가 더 이상 힌트 사용량을 받지 않는다
- 대조군을 돌렸다 — 기록에서 읽는 부분을 되돌리면 5개가, 사다리 순서 검사를 없애면
  1개가, 조건부 insert 로 되돌리면 1개가, `@Valid` 를 떼면 1개가 실패한다

### 남는 위험

- **아직 화면에 힌트 버튼이 없다.** API 는 있지만 눌러 볼 곳이 없다
- 힌트를 본 것이 `nextAction` 에 반영되지 않는다. Decision Engine 은 여전히 판정과
  mastery 만 본다 — "힌트를 다 보고도 틀렸다" 가 별도의 신호가 될 수 있지만,
  그것은 산식을 건드리는 일이라 여기서 하지 않는다
- 힌트를 보고 **제출하지 않으면** 아무것도 기록되지 않는다. `hint_usage` 에는 남지만
  Evidence 로 접히지 않는다 — 관측은 제출에 붙는다
