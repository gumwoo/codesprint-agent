# ADR-0018 · 진단은 문제를 고르는 순서지, 두 번째 채점기가 아니다

- 상태: 채택
- 날짜: 2026-09-07
- 정본 근거: PRD §56~58 · §88 · §114, [ADR-0001](0001-llm-analyzes-system-decides.md),
  [ADR-0002](0002-next-action-decided-by-rule-engine.md),
  [ADR-0009](0009-mastery-is-recomputed-from-evidence.md)

## 맥락

신규 사용자는 이력이 없다. `내 Skill` 화면을 열면 8개 전부 `mastery = –` 이고
뿌리 둘(`PYTHON_LIST_BASIC` · `PYTHON_DEQUE_BASIC`)만 `READY` 다. **그 둘 중
무엇부터인지는 화면도 서버도 말해 주지 않는다.** 시작점이 없다.

PRD 는 여기에 초기 진단을 둔다. 그런데 그 명세를 슬라이스 1 에 그대로 옮길 수 없다.

| PRD 가 전제하는 것 | 슬라이스 1 이 가진 것 |
| --- | --- |
| §58 · 14개 영역의 수준 추정 | 영역 하나(BFS Grid) + Foundations |
| §57 · 15~25 문제로 분기 | Skill 8개, 문제 15개 전부 `DEV_FIXTURE` |
| §56 · 목표 플랫폼 · 난이도 · 시험 날짜 · 하루 시간 | 그 값을 읽는 코드가 없다 |

없는 영역을 진단할 수 없고, 8개 Skill 에 15~25 문제를 낼 수도 없다. 그래서 **무엇을
남기고 무엇을 버렸는지** 적어 둔다 — 적지 않으면 나중에 이 축소판을 보고 "진단이
원래 이런 것이었나" 하게 된다.

## 결정

### 1. 진단은 추정기를 새로 만들지 않는다

**진단이 하는 일은 문제를 고르는 순서를 정하는 것뿐이다.** 푼 결과는 평소 제출과
같은 길을 지난다.

```
제출 -> Judge -> Evidence -> MasteryCalculator -> Skill 상태
```

진단 전용 점수도, 진단 전용 상태 전이도 만들지 않는다. 만들면 한 Skill 의 mastery 를
정하는 길이 둘이 되고, **둘은 반드시 갈린다** — 그때 어느 쪽이 정본인지 물으면 답이
없다. mastery 는 Evidence 에서 재계산되는 파생값이라는 규칙(ADR-0009)이 진단이라고
달라지지 않는다.

이것은 ADR-0001 이 그은 선과 같은 선이다. 진단은 **무엇을 물을지** 고르고, 얼마나
하는지는 산식이 정한다.

### 2. 분기는 선수 그래프로 한다

§57 의 분기형 진단에서 살아남는 것은 **전부 묻지 않는다** 는 발상이다. 영역별
난이도 조절은 영역이 하나뿐이라 옮길 것이 없지만, 선수 그래프는 같은 일을 한다.

```
어떤 Skill 을 통과했다  -> 그 선수들은 묻지 않는다 (함의)
실패했다               -> 선수로 내려간다        (원인)
```

`BFS_GRID_TRAVERSAL` 을 풀었다면 `GRID_COORDINATE` 를 따로 물을 이유가 없다. 실패했다면
그 아래 셋 중 어디서 막혔는지가 다음 질문이다. 그래프 깊이가 4 라, 8개를 다 묻는 대신
보통 3~4 문제에서 시작점이 나온다.

**끝나는 조건**(§88 "진단 종료 시점"): 모든 Skill 이 *평가됐거나* *함의됐을* 때.
문제 수 상한이 아니라 그래프가 덮였는지로 정한다.

### 3. 진단 결과는 확정이 아니라 시작점이다

Evidence 하나로 계산한 mastery 는 confidence 가 낮다. 그게 옳다 — 한 문제로 한 Skill 을
안다고 말할 수 없다.

그래서 진단은 **어디서부터 시작할지**만 정한다. 진단이 끝나도 Skill 은 `MASTERED` 가
되지 않고, 이후 제출이 같은 Evidence 열에 쌓이면서 값이 움직인다. 진단을 건너뛴
사용자와 마친 사용자가 **다른 상태 기계를 타지 않는다** — 앞선 쪽은 Evidence 가 몇 개
더 있을 뿐이다.

### 4. 쓰지 않을 값을 받지 않는다

§56 의 입력(목표 플랫폼 · 목표 난이도 · 시험 날짜 · 하루 가능 시간)을 받지 않는다.
읽는 코드가 없다. 받아 두면 사용자는 그 값이 반영된다고 믿는데 아무 데도 쓰이지 않는다.

힌트 사용량을 신고받다가 걷어낸 것과 같은 이유다 — **측정할 수 없는 것을 측정하지
않는다.** Planner(§89)가 생기면 그때 함께 받는다.

## 결과

- 신규 사용자에게 시작점이 생긴다. `내 Skill` 이 전부 `–` 인 상태에서 빠져나온다
- 진단 API 는 문제를 **고르고 순서를 기억할** 뿐이라 얇다. 채점 · 점수 · 상태 전이는
  이미 있는 것을 그대로 쓴다
- 슬라이스가 늘어 영역이 여럿이 되면 §57 의 영역별 분기가 다시 필요해진다. 그때
  이 ADR 을 갈음한다 — **지금 그것을 미리 만들지 않는다**

### 포기한 것

- **영역 간 수준 추정.** 영역이 하나라 비교할 대상이 없다
- **§57 의 15~25 문제.** Skill 8개에 그만큼 내면 진단이 아니라 학습이다
- **§56 의 온보딩 입력.** 소비자가 생길 때 받는다

### 남는 위험

- 문제 하나로 Skill 하나를 판단하므로, 그 문제를 우연히 맞히거나 우연히 틀리면
  시작점이 어긋난다. confidence 가 낮게 잡히고 이후 제출이 교정하지만, **첫 경로는
  틀릴 수 있다**
- 함의(통과 -> 선수 통과)는 그 Skill 이 정말 선수를 요구할 때만 옳다.
  `prerequisites.yaml` 이 틀리면 진단도 같이 틀린다. 그 데이터는
  `check_curriculum.py` 가 순환 · 미정의 참조만 막을 뿐, **관계가 사실인지는
  검증하지 않는다**
