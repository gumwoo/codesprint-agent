# ADR-0023 · 화면은 동작이 아니라 소유권을 검사한다

- 상태: 채택
- 날짜: 2026-09-09
- 정본 근거: [ADR-0017](0017-the-web-client-has-no-build-step.md),
  [ADR-0001](0001-llm-analyzes-system-decides.md)

## 맥락

화면 코드에서 나온 결함은 지금까지 **전부 한 종류였다.**

```
PR #20  버려진 폴러가 새 제출의 화면에 쓴다
PR #22  늦게 온 Skill 조회가 다른 사용자의 표를 그린다
PR #25  실행 결과가 뒤바뀐다 · 202 이전 요청이 남는다 · 목록에서 버튼이 되살아난다
PR #29  늦게 온 복습 조회가 "지금 복습하기" 를 되살린다
```

**여섯 번 나왔고 여섯 번 다 사람이 잡았다.** CI 에 남은 것은 하나도 없다.

원인은 두 가지였다.

1. **확인이 두 갈래였다.** "사용자가 바뀌었는가" 와 "더 새 요청이 있는가" 를 따로 두니
   한쪽만 확인하는 코드를 쓰게 된다 — 실제로 복습·진단·Skill 표가 전부 앞엣것만
   보고 있었다
2. **새 비동기 화면을 붙일 때마다 손으로 같은 것을 다시 만들었다.** 여섯 번째를 만들
   자리가 계속 생긴다

## 결정

### 1. 확인을 하나로 묶는다

```js
const mine = claimView("reviews");
const view = await getJson(...);
if (!mine()) { return; }
```

`claimView` 는 표를 주고, 그 표는 **사용자와 세대를 한꺼번에** 판단한다. 반쪽만 묻는
것이 불가능해진다.

접수(제출·실행)는 여기에 하나가 더 붙는다. 두 구간이 있기 때문이다.

```
요청 구간   POST -> 202          claimView 로 지킨다
관찰 구간   채점이 끝날 때까지    activeRunId / activeSubmissionId
```

**두 구간을 한 표로 묶을 수 없다.** 새 요청을 시작할 때 앞의 *요청*은 버려도 되지만
앞의 *관찰*은 살려야 한다 — 새 요청이 거절되면 앞 결과를 다시 볼 방법이 없다.
실제로 묶었다가 되돌렸다(PR #25).

### 2. 한 화면에는 주인이 하나다

**표를 받는 것만으로는 부족하다.** 같은 화면을 서로 다른 이름으로 차지하면, 각자는
규칙을 지키면서도 서로를 덮는다.

문제 화면으로 가는 길은 넷이다 — 직접 고르기 · 진단 · 복습 · 다음 문제. 이 넷이
`problem` 하나를 두고 다툰다. 처음에는 "다음 문제" 에 따로 통을 줬는데, 그러면 늦게
온 "다음 문제" 가 사용자가 방금 직접 고른 문제를 덮는다.

그리고 **화면을 떠나는 것도 소유권 변화다.** 문제 화면을 떠나면 진행 중인 이동을
놓는다 — 놓지 않으면 느리게 오던 문제가 도착해 사용자를 끌고 간다.

떠나는 경로마다 따로 적지 않고 `showLeft` 한 곳에서 놓는다. **경로마다 적으면 하나씩
빠뜨린다** — 실제로 목록은 놓았는데 "내 Skill" 탭은 놓지 않았다.

### 3. 표를 받았는지 CI 가 본다

`WebClientTest` 가 `app.js` 의 함수를 훑어, **네트워크를 기다리는 함수는 `claimView` 로
표를 받았는지** 확인한다. 예외 목록에는 이유를 함께 적는다 — 이유 없는 항목이 쌓이면
규칙이 아니라 예외가 코드를 지배한다.

**이 검사가 곧바로 세 곳을 찾았다.** 그중 `openProblem` 은 실제 결함이었다 — 문제를
빠르게 두 번 고르면 **마지막에 누른 것이 아니라 먼저 누른 문제가 열린다.** 브라우저로
재현했다.

## 왜 실제 브라우저를 CI 에 넣지 않는가

Playwright 를 넣으면 이 부류를 전부 잡을 수 있다. 그런데 그것은 [ADR-0017](0017-the-web-client-has-no-build-step.md)
을 갈음하는 결정이다 — npm 의존성과 두 번째 빌드 파이프라인이 들어온다.

지금 화면은 정적 파일 셋이고, 그 결정을 뒤집을 만큼 자란 상태가 아니다. 대신 **가장
자주 틀린 지점 하나**를 골라 정적으로 강제한다.

**이 검사가 못 잡는 것을 분명히 해 둔다.**

- 표를 받고도 **묻지 않으면** 잡지 못한다. 어디서 묻는지는 정적으로 확인할 수 없다
- **예외 목록이 틀린 것**도 잡지 못한다. `createUser` 를 "화면 조각이 아니다" 로
  빼 두었는데, 실은 <b>소유권이 가장 큰 변경</b>이었다 — 사용자를 바꾸면 화면 전체가
  따라간다
- **통이 지키는 축이 모자란 것**도 잡지 못한다. `claimView("problem")` 은 "어느 문제를
  보고 있는가" 를 지키지만 "어느 제출의 결정을 보고 있는가" 는 지키지 않는다 — 같은
  문제를 다시 내면 결과 패널만 갈리므로, 늦게 온 앞 제출의 자료가 새 제출의 결정
  요약 아래에 붙는다
- **통을 잘못 나눈 것**도 잡지 못한다. 같은 화면을 다른 이름으로 차지하면 각자는
  규칙을 지키면서 서로를 덮는다 — 실제로 `nextProblem` 과 `problem` 이 그랬고,
  검사는 통과했다
- 표를 **너무 늦게** 묻는 것(화면을 이미 쓴 뒤)도 잡지 못한다
- DOM 이 실제로 어떻게 그려지는지는 아무것도 보지 않는다

그 셋은 여전히 사람이 눌러 봐야 한다. 화면이 더 자라면 ADR-0017 을 갈음하고 실제
브라우저를 들이는 것이 맞다 — **이 ADR 은 그때까지의 중간 단계다.**

## 결과

- 확인 도구가 여섯 개 이름에서 두 개 개념으로 줄었다(`claimView` · `activeXId`)
- 새 비동기 화면을 붙이면 CI 가 표를 요구한다
- `openProblem` · `loadProblems` · `goToNextProblem` 이 이번에 표를 받았다
