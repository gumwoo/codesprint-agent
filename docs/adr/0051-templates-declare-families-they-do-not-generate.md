# ADR-0051 · 템플릿은 문제 가족을 적는다 - 문제를 만들지 않는다

- 상태: 채택
- 날짜: 2026-09-26
- 정본 근거: PRD §63(Problem Template System), §64(문제 소스 전략), §149(정답 암기 방지), §164(Template Schema),
  [ADR-0032](0032-the-agent-drafts-the-system-adopts.md), [ADR-0034](0034-the-road-to-the-full-prd.md)

## 맥락

PRD §63 은 "생성 문제는 템플릿을 가진다" 며 `GRID_CONNECTED_COMPONENT` 템플릿의 parameters(rows · columns ·
obstacleRatio · adjacency · requiredOutput)와 변형(영역 개수 · 영역 크기 · 최대 영역 …)을 예로 든다. §64 는
문제 소스를 A. 직접 검수 · B. 외부 링크 · C. 템플릿 생성 · D. LLM 생성으로 나눈다. §164 체크리스트에는
"Template Schema" 가 있다.

이 저장소의 문제는 D 다 - LLM 이 초안을 쓰고 채택 검사가 받는다(ADR-0032). 채택의 핵심은 **reference 와 다른
방식의 bruteForce 가 모든 입력에서 같다** 는 교차 검증이다. 템플릿이 parameters 로 문제를 찍어 내려면, 찍어 낸
변형마다 reference 와 bruteForce 가 있어야 한다 - 그것을 템플릿 하나가 모든 변형에 대해 맞게 갖는다는 보장이 없다.

## 결정

### 1. 템플릿은 가족과 변형 축을 적는 데이터다

`problems/templates.yaml`(계약 `contracts/problem-template.schema.json`)에 **이미 채택된 문제들**이 같은 가족이라는
것과, 가족 안에서 무엇을 바꿨는지를 적는다. 템플릿은 문제를 만들지 않는다 - 소스 C(템플릿 생성)는 두지 않는다.
생성은 지금처럼 D 가 하고, 템플릿은 D 가 만든 것 사이의 관계를 기록한다.

- `parameters` - 가족 안에서 바뀌는 값과 그 **축**. 축은 PRD §149 의 여섯(문제 서술 · 입력 구조 · 출력 요구 ·
  제약 조건 · 자료 표현 · 필요한 Secondary Skill) 중 하나다
- `variants` - 문제마다 parameters 의 값

처음 선언한 가족은 여섯이다 - 격자 영역(P02 · P03 · P04), 격자 최단 거리(P05 · P09 · P10), 그래프 BFS(P14 · P16),
구간 겹침(P106 · P107), 접두사 경계(P108 · P109), 두 무리 짝짓기(P124 · P125).

### 2. "숫자만 바꾼 변형" 을 CI 가 막는다

§149 "같은 패턴의 숫자만 바꾼 문제를 반복하지 않는다" 를 선언된 데이터 위에서 검사한다(`check_problems.py`).

| 규칙 | 깨뜨리는 메타테스트 |
| --- | --- |
| 변형의 문제가 있다 | 없는 문제를 가리키면 |
| 변형의 PRIMARY 가 템플릿의 Skill 이다 | 다른 Skill 을 재는 문제를 넣으면 |
| 한 문제는 한 가족이다 | 두 템플릿에 넣으면 |
| 변형은 parameters 의 값을 모두 적는다 | 값을 빠뜨리면 |
| **두 변형은 "제약 조건" 이 아닌 축 하나 이상에서 값이 다르다**(공백 · 대소문자는 무시) | 제약 조건 축만 다르게 하면 · 공백 · 대소문자만 다르게 하면 |
| 한 템플릿에 같은 문제를 두 번 적지 않는다 | 같은 문제를 두 번 적으면 |
| 템플릿 code · parameter 이름은 한 번씩 | code 를 두 번 · 이름을 두 번 적으면 |
| 템플릿의 Skill 이 있다 · 파일이 있다 | 없는 Skill · 파일을 지우면 |
| 변형은 둘 이상 · 축은 §149 의 여섯(계약) | 변형 하나 · 축을 여섯 밖으로 |

변형이 둘 이상이어야 하는 것과 축이 여섯 중 하나인 것은 계약이 보고, 그것도 메타테스트가 깨뜨려 본다.

## 남는 위험

- **검사는 선언한 가족에만 걸린다.** 채택 흐름과 생성기 프롬프트는 templates.yaml 을 요구하지도 참조하지도 않는다 -
  새 문제를 어느 가족에도 넣지 않으면 숫자만 바꾼 중복이 이 검사를 지나간다. 그 중복은 지금처럼 채택 뒤 스스로 점검과
  검증 에이전트가 찾는다. 이것은 §63 예시 같은 생성 파라미터 스키마가 아니라 **가족 레지스트리의 스키마**다
- 선언한 가족은 여섯뿐이다. PRIMARY 가 같은 문제가 둘 이상인 Skill 은 서른여섯이다(격자 경계 · 좌표 · 리스트 등은 아직
  적지 않았다)
- **선언을 믿는다.** 두 변형의 값이 다르다고 적었지만 실제로는 같은 계산일 수 있다 - 의미 중복은 지금처럼 채택 뒤
  스스로 점검과 검증 에이전트가 찾는다(W6~W9 에서 철회한 중복들). 템플릿 검사는 적은 것끼리의 모순만 잡는다
- 모든 문제가 가족에 속하지는 않는다. 같은 Skill 의 문제가 하나뿐이거나, 같은 Skill 이라도 한 가족으로 묶기 어려운
  문제는 적지 않았다
- 다음 문제를 고를 때(`NextProblemService`) 템플릿을 쓰지 않는다. 같은 Skill 의 다른 문제는 이미 다른 문제이고, 가족 안의
  어느 변형을 먼저 줄지 정할 근거(측정)가 없다
- 템플릿으로 문제를 찍어 내는 소스 C 는 만들지 않았다. 필요해지면 변형마다 reference · bruteForce 를 함께 만들고 채택
  검사를 그대로 지나게 해야 한다
