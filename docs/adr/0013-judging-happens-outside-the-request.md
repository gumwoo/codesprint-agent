# ADR-0013 · 채점은 요청 밖에서 일어나고, 큐의 정본은 DB 다

- 상태: 채택
- 날짜: 2026-09-05
- 정본 근거: Addendum §47, §67~68 / [ADR-0011](0011-language-boundary.md) / [ADR-0006](0006-expected-output-never-enters-sandbox.md)

## 맥락

PR #7 에서 제출 흐름을 처음으로 끝까지 이었는데, 채점이 **API 요청 스레드 안에서
동기로** 일어났다. `submit()` 전체가 하나의 `@Transactional` 이었고 그 안에서 Docker
컨테이너를 띄워 최대 120초를 기다렸다.

문제가 둘이다.

1. **DB 커넥션을 잡은 채로 외부 프로세스를 기다린다.** 동시 사용자가 몇 명만 되어도
   커넥션 풀이 사용자 수가 아니라 *채점 시간*에 따라 마른다. 느린 제출 하나가 아무
   상관 없는 요청까지 막는다.
2. **재시도할 방법이 없다.** 컨테이너 기동에 실패하면 그 제출은 그냥 사라진다.
   사용자에게는 `SYSTEM_ERROR` 가 보이고, 다시 내는 것 말고 할 수 있는 게 없다.

ADR-0011 은 이미 "경계는 큐다" 라고 정해 뒀다. 그 큐가 아직 없었을 뿐이다.

## 결정

### 1. 채점은 요청 밖에서 한다

```text
POST /submit          제출을 저장하고 큐에 넣는다. 202 로 즉시 돌려준다.
Judge Worker          큐에서 꺼내 컨테이너에서 실행하고 결과를 큐에 쓴다.
결과 적용             Evidence -> mastery 재계산 -> 다음 행동.
GET  /submissions/{id} 사용자가 결과를 확인한다.
```

요청 트랜잭션은 **제출 행 하나와 큐 행 하나를 쓰고 끝난다.** 채점 시간과 무관하다.

### 2. 큐의 정본은 `judge_jobs` 테이블이다

메시지 브로커를 두지 않는다.

- **이미 있는 것으로 충분하다.** PostgreSQL 의 `SELECT ... FOR UPDATE SKIP LOCKED` 는
  이 규모의 작업 큐에 필요한 것을 전부 준다 - 중복 없는 배정, 리스 만료, 재시도 횟수.
- **양쪽에서 읽을 수 있다.** Worker 는 Python 이다(ADR-0011). 브로커를 하나 더 두면
  두 언어에서 그 클라이언트를 각각 관리해야 한다.
- **제출과 큐가 같은 트랜잭션에 들어간다.** 별도 브로커였다면 "제출은 저장됐는데
  큐에 못 넣었다" 를 따로 다뤄야 한다(outbox 패턴이 푸는 그 문제다).

브로커가 필요해지는 시점은 처리량이 아니라 **채점기를 여러 대로 늘릴 때**다. 그때
바꾼다. 지금 바꾸면 아직 없는 문제를 위해 운영할 것이 하나 는다.

### 3. 언어 경계를 넘는 것은 그 테이블의 행 하나다

계약은 [`contracts/judge-job.schema.json`](../../contracts/judge-job.schema.json) 이다.
Java 가 쓰고 Python 이 읽는다. **정답(`expectedOutput`)은 여기에도 들어가지 않는다** -
Worker 가 `problems/<CODE>/cases.json` 을 직접 읽고, 컨테이너에는 현재 case 의 input 만
들어간다(ADR-0006).

## 결과

**좋아지는 것**

- 요청은 채점 시간과 무관하게 끝난다. 커넥션을 잡은 채로 기다리지 않는다.
- 실패한 채점을 다시 시도할 수 있다. 몇 번 시도했는지가 행에 남는다.
- Worker 가 죽어도 리스가 만료되면 다른 Worker 가 같은 job 을 가져간다.

**나빠지는 것**

- **API 가 결과를 바로 주지 않는다.** 클라이언트가 폴링해야 한다. 슬라이스 1 의
  화면이 아직 없으므로 지금 정하는 편이 낫다 - 나중에 바꾸면 이미 붙은 화면을 고쳐야 한다.
- **Worker 를 띄워야 한다.** 띄우지 않으면 제출이 `QUEUED` 로 남는다. 조용히
  성공한 것처럼 보이지 않도록, 오래된 `QUEUED` 는 상태로 드러난다.

**함께 생긴 시차**

- **결과를 반영하는 시점에는 그보다 나중의 제출이 이미 있을 수 있다.** 사용자 이력을
  보는 계산은 그 시차를 감안해야 한다 — §21-B 의 "최근 3문제" 가 그렇다. 창을 지금
  기준으로 잡으면 아직 일어나지 않은 문제가 창을 차지해, 실제로 있었던 재발이 보이지
  않는다. `SubmissionRepository.recentProblemIds` 가 제출 시각과 id 로 창을 자른다.
- **반영은 자리를 먼저 잡고 시작한다.** 읽고 확인한 뒤 쓰면 두 인스턴스가 나란히
  "아직 반영 안 됐다" 를 보고 둘 다 반영한다. Evidence 는 유일성이 막지만(ADR-0009)
  탐지 기록에는 그런 열쇠가 없어 같은 제출에 분석이 여럿 남는다 —
  `JudgeJobRepository.claimForApply` 가 조건부 UPDATE 로 자리를 잡는다.
- **자리는 끝난 job 에만 내준다.** 채점 중인 job 을 반영하면 결과를 읽지 못해
  `SYSTEM_ERROR` 가 되는데, 그건 예외가 아니라 정상 처리라 **커밋된다.**
  `applied_at` 이 남아 다시 집지 않으므로 나중에 도착할 진짜 결과를 영원히 잃는다.
  후보를 고르는 쪽에만 조건을 두면 잘못된 호출 한 번이 그렇게 된다 — 버릴 수 있는
  쪽에서 막는다.

**바뀌지 않는 것**

- 판정의 의미, Evidence 매핑, mastery 산식, Decision 규칙은 그대로다. 옮긴 것은
  **언제 어디서 실행되는가** 뿐이다.
- 샌드박스 격리도 그대로다. Worker 는 `judge/run_submission.py` 를 그대로 쓴다.

## 대안

**요청 스레드에서 비동기로만 돌린다(`@Async`).** 커넥션은 풀리지만 재시도가 없고,
프로세스가 죽으면 진행 중이던 제출이 사라진다. 큐 행이 있으면 그것이 남는다.

**Redis / RabbitMQ.** 위에 적은 이유로 지금은 아니다. 바꿀 때 갈아끼울 지점은
`JudgeJobQueue` 하나다.
