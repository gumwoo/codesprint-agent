# ADR-0059 · 사용자 프로그램은 작은 실행기의 fork 에서 시작한다 - memoryKb 는 그 프로그램의 것이다

- 상태: 채택
- 날짜: 2026-09-28
- 정본 근거: [ADR-0005](0005-judge-stops-at-first-failure.md)(하네스는 이미지에 굽는다),
  [ADR-0055](0055-each-case-starts-with-the-harness-alone.md), [ADR-0056](0056-the-time-limit-takes-no-slot-and-one-place-reaps.md) D

> 번호: 0057 은 동시에 진행 중인 다른 브랜치가 쓸 수 있어(ADR-0058 이 비워 둔 자리) 0059 로 잡았다.

## 맥락

ADR-0056 D 가 원인을 쟀다. memoryKb 는 `wait4` 의 `ru_maxrss` 인데, 하네스(파이썬)가 사용자 프로그램을 직접
`fork` 하므로 자식은 하네스의 사본으로 시작하고, 커널은 exec 할 때 그 사본의 최고 RSS 를 프로세스의 maxrss 에
남긴다. 그래서 값이 `max(fork 순간 하네스의 사본, 사용자 프로그램의 최고 RSS)` 였다. 하네스보다 작은 풀이는 하네스
크기로 보이고, 입력이 큰 case 는 하네스가 쥔 입력 사본까지 더해졌다. 판정에는 들어가지 않는 표시값이라 0056 은
고치지 않고 후보만 적었다.

이 ADR 전에 다시 잰 값(아래 표의 "main")도 같다. 작은 C++ 풀이는 자기 최고 RSS 가 약 3.1MB 인데 9.4MB 로, 4.5MB
입력을 조금씩 읽고 버리는 같은 풀이는 23.6MB 로 보였다.

## 결정

**사용자 프로그램은 하네스가 아니라 이미지에 구운 작은 실행기(`judge/runner/launch.c` → `/opt/judge/launch`)의
`fork` 에서 시작한다.** 실행기는 기다리지 않는다.

```text
하네스  Popen([launch, fd, *run])                 실행기(정적 링크, 약 640KB)
실행기  fork -> 자식이 run 을 exec                 자식의 maxrss 바닥 = 실행기의 사본
실행기  fd 에 "pid <n>" 을 적고 곧바로 끝난다
하네스  wait4(실행기), fd 를 EOF 까지 읽는다        EOF = 자식이 exec 했다(fd 는 close-on-exec)
        자식은 PID 1(하네스)에게 넘어와 있다
하네스  pidfd_open(자식) + setitimer               ADR-0056 과 같다
        입력을 쓴다, wait4(자식)                   거두는 곳은 여전히 여기 하나
```

- **실행기는 종료 상태도 rusage 도 전달하지 않는다.** 부모가 끝나면 자식은 PID 1 인 하네스에게 넘어오므로(하네스가
  컨테이너의 PID 1 인 것은 ADR-0055 가 이미 기대는 사실이다) 하네스가 그 pid 로 직접 `wait4` 한다. 종료 코드 ·
  신호(`-9` · `-25`) · `ru_maxrss` 는 전처럼 커널이 사용자 프로그램의 것을 준다. 시간 제한 신호도 전처럼 pidfd 로
  사용자 프로그램에게 간다 - 실행기가 사이에서 신호를 전달하거나 종료 상태를 흉내 내는 코드가 없다.
- **시간을 재는 방식은 그대로다. 재는 값은 실행기 몫(0.3~0.7ms, 아래 측정)만큼 늘었다.** `started` 는 전처럼 띄우기 직전, 타이머는 전처럼 exec 가 끝난 뒤에 건다 - 전에는
  `subprocess.Popen` 이 자식의 exec 를 기다린 뒤 돌아왔고, 이제는 fd 의 EOF 가 같은 순간을 알려 준다.
- **자식을 띄운 뒤 새 태스크를 만들지 않는다**(ADR-0056)는 그대로다. 실행기를 거두고 pid 를 읽는 것은 fd 와 `wait4`
  뿐이다. 실행기는 사용자 프로그램이 도는 동안 이미 거둬져 자리를 쓰지 않는다.
- `RLIMIT_FSIZE` 는 전처럼 `preexec_fn` 으로 걸고(이제 실행기에), 사용자 프로그램이 물려받는다. 사용자 프로그램이
  받는 fd 는 전처럼 0 · 1 · 2 뿐이다.
- exec 가 실패하면 자식이 fd 에 `exec <errno>` 를 적고, 하네스는 전에 `Popen` 이 `FileNotFoundError` 로 죽던 것처럼
  죽는다 - `SYSTEM_ERROR` 다. 사용자 코드의 `RUNTIME_ERROR` 로 둔갑하지 않는다.
- 실행기는 세 이미지가 같은 멀티 스테이지 줄로 굽는다(`FROM gcc:13-bookworm AS launcher`, `gcc -O2 -static`).
  컴파일러는 최종 이미지에 들어가지 않는다. `.dockerignore` 는 `launch.c` 를 더 남긴다.

`DOCKER_LIMITS` · `MOUNT_MODE` · `memory_limits()` 는 바꾸지 않았다. 판정 분기(`MEMORY_LIMIT` 은 SIGKILL 과
`MemoryError` 류로 정한다)도 그대로다.

### 선택지

| 후보 | 판단 |
| --- | --- |
| **작은 정적 실행기, 기다리지 않는다** | 채택. 바닥이 약 640KB 로 내려가고, 거두기 · 신호 · 종료 상태가 전과 같은 경로로 사용자 프로그램에게서 온다 |
| 작은 정적 실행기가 기다려 rusage 를 파이프로 돌려준다 (0056 의 첫 후보) | 버림. 시간 제한 신호가 실행기에 가서 전달 코드가 필요하고, 종료 코드 · 신호를 실행기가 흉내 내야 한다. 실행기를 죽이면 rusage 도 잃는다 |
| `sh` 로 손자를 띄우고 셸은 곧바로 끝낸다 | 버림. 비대화형 셸의 백그라운드 작업은 SIGINT · SIGQUIT 를 무시로 두고 표준 입력을 /dev/null 로 바꾼다 - 무시 설정은 exec 를 넘어 **사용자 프로그램이 물려받는다.** 우회하면 셸마다(dash · bash) 다른 규칙에 기대게 된다 |
| 하네스가 입력을 쥐지 않은 채 fork 한다 (memfd) | 버림. 입력 사본만 뺀다. 하네스 기본 크기(9.6~14.7MB, 아래)는 남는다 |
| `posix_spawn` · `vfork` | 버림. 자식이 부모의 주소 공간을 쓴 채 exec 하므로 부모(하네스)의 최고 RSS 를 통째로 물려받는다 - 더 나쁘다 |
| cgroup `memory.peak` | 버림. 컨테이너 cgroup 에는 하네스가 함께 있다. 하위 cgroup 을 만들려면 cgroupfs 를 쓰기 가능으로 여는 컨테이너 옵션이 필요하다 |
| 끝나기 직전의 `/proc/<pid>/status` VmHWM 을 읽는다(ptrace exit-stop) · 돌 때 주기적으로 읽는다 | 버림. 앞쪽은 사용자 프로그램을 추적하게 되어 신호 의미가 바뀌고, 뒤쪽은 마지막 읽기 뒤의 최고값을 놓친다 |
| `clear_refs` 에 5 를 써 최고 RSS 를 되돌린다 | 버림. 되돌리는 것은 주소 공간의 최고값뿐이고 현재 RSS(= 하네스 사본)는 그대로라, exec 때 남는 값이 같다 |

## 측정

사용자 프로그램이 `/proc/self/status` 의 `VmHWM`(exec 뒤 주소 공간의 최고 RSS)을 스스로 적고 끝나게 해, 그 값과
memoryKb 를 나란히 쟀다. `main` 은 이 브랜치의 기준 커밋(37c5c8d)의 하네스로 구운 이미지다. 각 7 회 중앙값, Docker
Desktop(WSL2 커널 6.6).

| 조건 | 프로그램 VmHWM | memoryKb (main) | 차이 (main) | memoryKb (이 ADR) | 차이 (이 ADR) |
| --- | --- | --- | --- | --- | --- |
| Python 작은 풀이 | 9,532KB | 13,116KB | +3,584 | 9,728KB | +272 |
| C++ 작은 풀이 | 3,144KB | 9,416KB | +6,272 | 3,456KB | +324 |
| Java 작은 풀이 | 35,060KB | 35,036KB | -24 | 35,032KB | +12 |
| Python, 50MB 를 쥐는 풀이 | 60,736KB | 60,928KB | +192 | 60,928KB | +192 |
| Python, 4.5MB 입력을 한 줄씩 읽고 버림 | 9,640KB | 24,424KB | +14,784 | 9,728KB | +176 |
| C++, 4.5MB 입력을 64KB 씩 읽고 버림 | 3,196KB | 23,636KB | +20,440 | 3,584KB | +392 |

VmHWM 열은 두 실행에서 각각 잰 값의 중앙값이 거의 같아(차이 100KB 안) 앞 실행의 것을 적었다. 남는 +150~+550KB 는
프로그램이 VmHWM 을 읽은 **뒤**(출력하고 끝나는 동안) 쓴 것과 커널 RSS 카운터의 근사 차이로 본다 - 둘을 나눠 재지는
않았다. Java 와 50MB 풀이처럼 하네스보다 큰 프로그램은 전에도 맞았고 지금도 같다.

바닥도 쟀다. 아무것도 하지 않고 끝나는 프로그램의 `ru_maxrss` 는 하네스가 직접 띄우면 그 이미지의 하네스 사본
크기(py312 14,692KB · cpp 10,368KB · java21 9,600KB), 실행기로 띄우면 640KB 다(`/bin/true` 는 1,024~1,152KB).

**시간.** 같은 작은 풀이를 20 case 씩 main 과 번갈아 4 번 돌린 case 별 executionMs 중앙값은 Python 21 → 20ms,
C++ 2 → 2ms, Java 78 → 80.5ms 다(각 80 case). `--cpus 0.5` 에서의 잡음(평균은 한 번 돌릴 때마다 수십 ms 움직인다)
안이다.

띄우기만 따로 쟀다. 컨테이너 안에서(PID 1, `--cpus 0.5`) 옛 방식(하네스가 직접 `Popen`)과 새 방식(`_spawn`)을
번갈아 60 번씩 띄우고 거둔 시간의 중앙값은 `/bin/true` 1.19 → 1.51ms, `python3 -c pass` 10.92 → 11.59ms 다 -
실행기의 exec 와 fork 하나만큼(0.3~0.7ms) 늘었다. 이 비용은 executionMs 에 들어간다.

**판정.** 문제 116 개의 풀이 307 개(reference 116 · wrong 116 · skill_control 65 · probes 10)를 main 이미지와 이
이미지로 번갈아 채점해 대 봤다. **판정 · failedCaseId · case 별 판정이 307 개 모두 같다**(ACCEPTED 116 ·
WRONG_ANSWER 107 · TIME_LIMIT 67 · RUNTIME_ERROR 17). memoryKb 차이(이 ADR - main)의 중앙값은 -208KB, 범위는
-3,788 ~ +636KB 다. 문제 풀이는 대부분 파이썬 프로그램 자신이 하네스 사본(약 13MB)과 비슷하거나 커서 많이 줄지 않았고,
가장 많이 준 것은 작은 풀이들이다(P37 reference 13,260 → 9,472KB). 풀이별 최대 executionMs 는 둘 다 ACCEPTED 인
116 개에서 차이 중앙값 +3.5ms(사분위 -5 ~ +13.75ms, 늘어난 것 71 · 줄어든 것 43)다. 위의 0.3~0.7ms 보다 크게
나온 부분은 `--cpus 0.5` 의 잡음과 구별하지 못했다.

## 검사

`test_judge.py` 에 **memoryKb 는 사용자 프로그램 자신의 것이다** 를 넣었다. 프로그램이 스스로 읽은 VmHWM 을 출력하고,
memoryKb 가 `VmHWM - 512KB ~ VmHWM + 1024KB` 안이어야 한다. 세 경우를 본다 - C++ 작은 풀이(하네스 사본이 섞이면
+6MB), 4.5MB 입력을 받는 같은 C++ 풀이(하네스가 쥔 입력이 섞이면 +20MB), Python 작은 풀이(+3.5MB). 아래쪽 경계는
실행기(약 640KB)처럼 다른 프로세스를 재는 쪽으로 틀리는 것을 잡는다. 프로그램이 숫자를 출력하지 못하면
`[VACUOUS]` 로 실패한다. 이 검사를 30 번(3 경우 x 10) 돌린 차이는 +160~+540KB 였다.

**fix 를 되돌리면 깨진다.** `harness.py` · 세 Dockerfile · `.dockerignore` 를 기준 커밋(37c5c8d)으로 되돌리고 세
이미지를 다시 구워 이 검사만 돌렸다. 세 경우 모두 실패했다 - C++ 작은 풀이 memoryKb 9,412 / VmHWM 3,180,
C++ 큰 입력 23,908 / 3,228, Python 작은 풀이 13,228 / 9,564. 되돌린 것을 복원하고 다시 구운 이미지로는 통과한다.

ADR-0056 의 게이트 두 개(`pids` · `reap`)도 고쳤다. 이제 `Popen` 으로 띄우는 것은 사용자 프로그램이 아니라
실행기다.

- **`pids` 게이트는 실행기를 거둔 뒤에 선다.** 처음에는 인자가 `RUN` 으로 끝나는 `Popen` 직후에 세웠는데, 그때는
  아직 거두지 않은 실행기가 자리 하나를 쥐고 있다. 게이트가 열린 뒤 `_spawn` 이 실행기를 거두면 자리가 하나 비고,
  채우는 제출은 fork 가 처음 실패한 곳에서 멈췄으므로 그 자리를 다시 채우지 않았다. 그래서 **자식을 띄운 뒤 스레드를
  하나 만드는 회귀가 든 하네스도 이 검사를 통과했다**(PR #74 검토에서 변이로 찾았고, 같은 변이로 2/2 통과를 다시
  확인했다). 지금은 게이트가 실행기 pid 에 대한 `wait4` 가 돌아온 뒤 `pids.current >= pids.max` 를 기다리고, 채우는
  제출은 게이트가 열릴 때까지 fork 를 되풀이한다. `RUN` 을 직접 띄우는 옛 하네스에서는 전처럼 `Popen` 직후에 선다.
- **`reap` 게이트**가 붙잡을 pid 는 하네스가 `pidfd_open` 에 넘기는 pid(시간 제한의 대상)로 안다. 옛 하네스에서는
  전처럼 `Popen` 의 pid 다.

고친 게이트로 네 경우를 각 2 번 돌렸다. 변이는 `run_case` 에서 자식을 띄운 직후(이 하네스는 `_spawn` 뒤, main 은
`_arm_hard_limit` 앞) 스레드 하나를 만들고 join 하는 것이고, 별도 태그로 구워 검사 뒤 지웠다.

| 하네스 | `pids` 게이트 (exit · spin) |
| --- | --- |
| 이 하네스 | 통과 |
| 이 하네스 + 변이 | 실패 - 둘 다 `SYSTEM_ERROR` (하네스가 스레드를 못 만들어 죽는다) |
| main 하네스 | 통과 (ADR-0056 이후라 통과가 맞다) |
| main 하네스 + 변이 | 실패 - 둘 다 `SYSTEM_ERROR` |

`reap` 게이트는 이 하네스와 main 하네스 모두에서 통과했다.

## 남는 위험

- **하네스가 PID 1 이 아니면 사용자 프로그램을 거두지 못한다.** 실행기가 끝나면 자식은 가장 가까운 subreaper, 없으면
  pid namespace 의 init 에게 간다. 채점 컨테이너에서는 하네스가 init 이다(ENTRYPOINT, `--init` 없음). 하네스를
  다른 프로세스 아래에서 돌리면 `wait4` 가 `ChildProcessError` 로 하네스를 죽인다 - 조용히 틀린 값이 아니라
  `SYSTEM_ERROR` 로 드러난다. `--init` 을 붙이는 변경은 이 ADR 과 ADR-0055 를 함께 다시 봐야 한다.
- 신뢰 경계 안에 네이티브 코드가 늘었다(주석을 빼면 30 줄 남짓). 권한 없이 runner uid 로 돌고, 사용자 입력을 읽지 않는다(인자는
  하네스가 만든다).
- 실행기 바닥(약 640KB)보다 작은 프로그램은 그 값으로 보인다. 채점 이미지의 가장 작은 C++ 풀이도 약 3MB 라 실제로는
  닿지 않는다.
- 이미지를 굽는 데 `gcc:13-bookworm` 이 필요하다(C++ 이미지의 기반이라 이미 받는 이미지다). 정적 링크라 최종
  이미지의 libc 와는 무관하다.
- memoryKb 가 작아졌다. 이전 제출의 저장된 값과 이후 값은 같은 기준이 아니다 - 작은 풀이는 3~6MB, 입력이 큰 case 는
  입력 크기의 몇 배만큼 줄었다. memoryKb 는 판정 · Evidence · mastery 에 들어가지 않는다(ADR-0056 D).
