# ADR-0049 · 학습 분석 · 시험 전략 · Evaluator - PRD §164 의 남은 조각

- 상태: 채택
- 날짜: 2026-09-26
- 정본 근거: PRD §93(Evaluator Agent), §95(Exam Strategy Agent), §99(핵심 화면 Analytics), §160(Learning
  Analytics), §164(구현 체크리스트), [ADR-0001](0001-llm-analyzes-system-decides.md),
  [ADR-0034](0034-the-road-to-the-full-prd.md), [ADR-0038](0038-the-plan-is-decided-not-generated.md),
  [ADR-0043](0043-mock-test-and-learning-modes.md)

## 맥락

ADR-0034 의 웨이브 W1~W9 를 마친 뒤 PRD §164 체크리스트를 main 과 대조했다. 웨이브 표에 없던 항목이 남았다 -
Agent 의 Evaluator · Exam Strategy, UX 의 Analytics, Problem 의 Template Schema. 여기서는 앞의 셋을 다룬다.
Template System(§63)과 Explain Back(§148)은 다음 결정에서 다룬다.

## 결정

### 1. Evaluator(§93)는 이미 있다 - 시스템이다

PRD §93 은 Evaluator 를 "Judge 결과 · 힌트 사용량 · 풀이 시간 · 재시도 · Reviewer 결과를 받아 Skill State 를
갱신한다" 고 적는다. ADR-0001 대로 점수와 상태를 LLM 에게 묻지 않으므로, 이 역할은 처음부터 시스템이 한다.

| §93 의 입력 | 받는 곳 |
| --- | --- |
| Judge 결과 | `JudgeResultPoller` → `JudgeResultApplier` |
| 힌트 사용량 | 제출 행에 얼린 최고 단계(ADR-0027) → `SubmissionEvidenceFactory` |
| 풀이 시간 | 제출의 `solveSeconds` → `SubmissionEvidenceFactory` |
| 재시도 | 같은 문제의 연속 실패(`findStatusesNewestFirst`) → `DecisionEngine` |
| Reviewer 결과 | `ReviewService` → `MistakeConfirmation` · `CaseCorroboration`(확정은 시스템, ADR-0014 · 0015) |
| Skill State 갱신 | Evidence 에서 재계산하는 `MasteryCalculator`(ADR-0009) |

새 코드를 만들지 않는다. §164 의 "Evaluator" 는 이 표로 체크한다.

### 2. Exam Strategy(§95) - 넷 중 둘은 있었고 둘을 더한다

| §95 가 정하라는 것 | 결정 |
| --- | --- |
| 새 유형 학습 여부 | 이미 있다 - 시험 7 일 이하면 새로 배우지 않는다(ADR-0038 §3) |
| 복습 우선순위 | 이미 있다 - 만기 복습을 예산과 상관없이 맨 앞에(ADR-0038) |
| **Mock Test 빈도** | 시험 모드에서 **최근 7 일 안에 시작한 모의 시험이 없으면** 오늘의 계획에 `MOCK_TEST` 블록을 복습 다음, 연습 앞에 둔다 |
| **문제 포기 전략** | 포기 기준은 **연 뒤 그 문제의 기대 풀이 시간**이다. 보고서가 문제마다 `lateGiveUp` 을 준다 - 기준을 넘긴 **뒤에도 실행 · 제출이 있었고** 끝내 풀지 못했으면 true, 풀었거나 기준을 넘긴 뒤 손대지 않았으면 false, 채점 중이거나 안 열었으면 null |

- 빈도는 "시험 모드 기간(7 일)에 한 번" 이다. 더 잦은 빈도를 정할 근거가 되는 측정이 없다 - ExamFrequency 를
  쓰지 않은 것과 같은 이유다(ADR-0038 §2)
- 모의 시험 블록의 길이는 `MockTestService.dueMinutes` 가 실제로 만들 시험과 **같은 후보 · 같은 구성 규칙**으로
  잰다. 계획이 말한 시간과 시험 탭이 여는 시험의 시간이 같다(테스트가 본다)
- 모의 시험은 쪼갤 수 없다. 진단 · 복습을 넣고 남은 하루 시간에 들어가지 않으면 넣지 않고, **이유 문장을 만들기
  전에** 뺀다 - 이유가 넣지 않은 블록을 "채웠다" 고 말하지 않게
- 포기 기준을 새로 어림하지 않는다. 기대 풀이 시간은 문제 데이터다(채택 검사가 받는 값). 보고서는 시험이 끝난
  뒤에만 주므로 시험 중에 기준이 문제의 난이도를 알려 주지 않는다
- **"포기가 늦었다" 는 관측한 것으로만 말한다.** 서버가 보는 것은 연 때 · 실행 · 제출 시각뿐이다. 처음에는 "연 때부터
  끝날 때까지의 경과" 로 판정해, 열어 보고 30 초 만에 다른 문제로 간 사람도 "포기가 늦었다" 를 받았다(검증 에이전트가
  재현했다). 채점 중이면 결과를 모르므로 null 이다
- **모의 시험 블록을 줄 때는 곧 만들 시험의 문제를 계획에서 뺀다.** 시험 후보(처음 보는 · 잠기지 않은 일반 문제)가
  계획의 연습 · 진단 문제와 겹쳐, 계획이 보여 준 문제가 시험에 들어갔다(검증 에이전트가 15 경우 중 12 에서 재현).
  계획과 시험은 같은 결정적 규칙(`MockTestService.upcoming`)으로 문제를 정하므로, 계획을 받은 시점의 시험과 겹치지
  않는다. 뺀 뒤 줄 문제가 없는 Skill 은 계획에 넣지 않는다

### 3. 학습 분석(§99 · §160) - 저장된 관측만 센다

`GET /api/users/{id}/analytics` 와 화면의 "분석" 탭.

- 판정 분포(0 인 판정도 칸으로), 채점 중 제출 수
- 푼 문제 수와 그중 **Evidence 와 같은 기준**(힌트 H4 미만 · 전체 풀이 없음)으로 도움 없이 푼 문제 수
- 최근 8 주의 주별 제출 · ACCEPTED 수(월요일 시작, UTC - 오늘의 계획과 같은 날짜 기준)
- 트랙 안 Skill 의 상태별 수
- 끝난 모의 시험 최근 10 개와 푼 수(보고서와 같은 분석으로 센다)

예측 · 점수 · 추세선은 없다. 화면은 세지 않는다 - 서버가 준 수를 표로 적는다(ADR-0017 · 0023 의 "화면은 판단하지
않는다"). 시험 중에는 409 다 - 상태 분포와 판정 분포를 시험 제출 전후로 비교하면 시험 문제의 유형이 드러난다
(`ExamLock`, ADR-0043 과 같은 이유). PRD §123 의 오답 분석(최근 50 제출)은 이미 오늘 탭에 있다(ADR-0038).

## 남는 위험

- 계획은 받은 시점의 것이다. 계획을 본 뒤 다른 문제를 내면 시험 후보가 바뀌어, 이미 떠 있는 계획의 모의 시험 길이와
  실제 시험 길이가 달라질 수 있고 드물게 떠 있는 계획의 문제가 새 시험에 들어갈 수 있다 - 다시 받은 계획은 맞다
- ExamLock 은 처음에 `[0-9]{1,18}` 에 맞지 않는 userId 를 그냥 통과시켜, `+1` · `0x1` · 앞 공백 표기로 시험 중에
  오늘 탭 · 분석이 열렸다(검증 에이전트). 이제 컨트롤러와 같은 변환(`NumberUtils.parseNumber`)으로 읽는다

- 주는 UTC 로 자른다. 한국 시간 월요일 새벽의 제출은 앞 주로 들어간다 - 오늘의 계획도 UTC 날짜를 쓰므로 둘은 같다
- "최근 7 일" 의 모의 시험은 시작 시각으로 센다. 시험 모드에 들어가기 직전에 본 시험도 세므로, D-8 에 본 사람은
  D-1 까지 블록을 받지 않는다
- 포기 기준(기대 풀이 시간)은 채택 때 초안이 적은 값이다. 실제 사용자 풀이 시간으로 보정하지 않았다
- Template System(§63) · Explain Back(§148) · JavaScript · Kotlin 러너(§67)는 아직 없다
