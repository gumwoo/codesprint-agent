# ADR-0028 · 안내받는 길을 끝에서 끝까지 걸어 본다

- 상태: 채택
- 날짜: 2026-09-13
- 정본 근거: [ADR-0002](0002-next-action-decided-by-rule-engine.md),
  [ADR-0019](0019-diagnostic-is-an-input-to-the-decision-engine.md),
  [ADR-0021](0021-a-review-is-what-the-schedule-says.md),
  [ADR-0022](0022-unlock-next-names-where-to-go.md)

## 맥락

규칙은 하나씩 검사받고 있었다. 복습이 일정으로 정해지는가, 개념 자료가 붙는가,
`MASTERED` 다음에 갈 곳이 있는가 — 전부 테스트가 있다.

**그런데 전부 테스트가 문제를 손으로 골라 놓고 그 규칙만 확인한다.**
`ReviewLoopTest.reachTheThreshold()` 는 `P05_SHORTEST_PATH` 를 아홉 번 푼다. 그 아홉
번을 누가 고르라고 했는지는 아무도 묻지 않았다.

그래서 확인된 적 없는 것이 하나 남아 있었다 — **그 규칙들을 이어 붙이면 실제로
어딘가에 도착하는가.** 이 저장소의 주장이 "가장 짧은 경로로 독립 풀이 가능한
상태까지" 인데, 그 주장 자체는 검사받지 않고 있었다.

## 결정

**아무것도 고르지 않는 테스트를 둔다**(`GuidedJourneyTest`).

문제 목록을 보지 않는다. 진단이 준 첫 문제에서 출발해, 그다음부터는 매번
`nextAction` 이 가리키는 곳으로만 간다. 화면이 가진 입구를 그대로 쓴다 — 진단,
만기 복습, 직전 제출의 결정.

테스트가 하는 유일한 개입은 **시계를 미는 것**이다. 간격 복습은 최소 하루를
기다려야 하므로(ADR-0021) 그러지 않으면 이 길은 절대 끝나지 않는다. 무엇을 풀지는
여전히 고르지 않는다.

### 걸음 수에 상한을 둔다

**제자리를 도는 것도 실패다.** 갈 곳이 늘 있는데 아무 데도 도착하지 않는 길은,
갈 곳이 없는 길보다 알아채기 어렵다.

### 도착만 보지 않는다

테스트가 둘인 이유다.

```
도착했는가        MASTERED 에 닿는가
가는 동안         갈 곳 없는 걸음이 한 번도 없었는가
```

도착했다는 것이 중간에 빈 화면이 없었다는 뜻은 아니다. **사용자는 그 빈 화면에서
멈춘다.**

## 첫 실행이 찾은 것

열두 걸음 중 **여덟 걸음이 갈 곳이 없었다.**

```
진단 -> P05_SHORTEST_PATH
CONTINUE -> (문제 없음: 같은 문제를 이어서 푼다 - 새 문제를 고르지 않는다)   x8
SCHEDULE_REVIEW -> (문제 없음)
시계를 민다
복습 -> P10_BFS_REVIEW
```

`CONTINUE` 는 "같은 문제를 이어서 푼다" 는 뜻이다(`NextProblemService`).
`SYSTEM_ERROR` 와 `COMPILE_ERROR` 에서는 맞다 — 고쳐서 다시 내면 된다.

**그런데 정답 분기에서도 같은 행동이 나왔다.** 방금 맞힌 문제에 이어서 풀 것은 없다.
그래서 화면은 아무 문제도 주지 못하고, 사용자는 목록으로 돌아가 직접 고르게 된다.
"에이전트가 데려간다" 가 여덟 번 중단된 것이다.

### 고침

정답이지만 아직 문턱 아래일 때 `RETRY_VARIANT` 를 낸다 — 이미 있던 행동이고
"같은 Skill 의 다른 문제로 연습한다" 는 뜻이다.

**같은 Skill 에 머무는 것은 그대로다.** 달라지는 것은 어디에 머물지 말해 준다는
것뿐이다. `SYSTEM_ERROR` / `COMPILE_ERROR` 의 `CONTINUE` 는 건드리지 않았다.

고친 뒤의 길은 열두 걸음이고, 갈 곳 없는 걸음은 `SCHEDULE_REVIEW` 하나다 —
그 자리에서 할 일이 **기다리는 것**이므로 맞다.

```
진단 -> P05_SHORTEST_PATH
RETRY_VARIANT -> P09_BFS_VARIANT_A / P05_SHORTEST_PATH  (번갈아 8번)
SCHEDULE_REVIEW -> (기다린다)
복습 -> P10_BFS_REVIEW
=> MASTERED
```

같은 문제가 다시 나오는 것은 의도된 동작이다 — `BFS_SHORTEST_PATH` 의 NORMAL 문제가
둘뿐이고, `pick` 이 "전부 스스로 푼 적이 있어 다시 낸다" 로 적어 두고 있다.

## 왜 이것을 단위 테스트가 못 잡았는가

`DecisionEngineTest` 는 이 분기를 **정확히 검사하고 있었다.** "문턱 아래면 CONTINUE"
라고, 통과하는 채로.

규칙 하나만 보면 `CONTINUE` 는 틀리지 않는다 — "이 Skill 에 머문다" 는 뜻으로 읽으면
맞다. 틀린 것은 **그 행동을 문제로 옮기는 쪽과 이어 붙였을 때**다. 두 곳이 같은
이름을 다르게 읽고 있었고, 각자의 테스트는 각자 통과했다.

이 저장소가 반복해서 만난 결함 부류와 같다 — **문서가 주장하는 것과 코드가 강제하는
것의 간극.** 여기서는 두 코드가 서로에 대해 주장하고 있었다.

## 결과

- 새 사용자가 에이전트만 따라 걸어 `MASTERED` 에 닿는 것이 처음으로 확인됐다
- 정답 뒤의 갈 곳 없는 액션이 닫혔다. 남은 것은 `SCHEDULE_REVIEW` 하나이고 의도된 것이다
- `MovableClock` 을 `dev.codesprint.support` 로 꺼냈다. 두 테스트가 같은 것을 쓴다

### 남는 위험

- **한 갈래만 걷는다.** 전부 `ACCEPTED` 로 푸는 길이다. 틀리는 길(드릴 · 개념 복습)은
  다른 테스트가 조각으로 보고 있고, 여기서 이어 붙이지 않았다
- **"가장 짧은" 은 검사하지 않는다.** 도착하는지만 본다. 열두 걸음이 최선인지는
  이 테스트가 말하지 않는다
- 걸음 상한(60)은 임의의 값이다. 지금 길이 열두 걸음이라 넉넉하지만, 커리큘럼이
  늘면 다시 봐야 한다
