# ADR-0025 · 화면의 비동기 순서는 실제 브라우저로 검사한다

- 상태: 채택
- 날짜: 2026-09-13
- 정본 근거: [ADR-0017](0017-the-web-client-has-no-build-step.md),
  [ADR-0023](0023-the-screen-checks-ownership-not-behaviour.md)

## 맥락

[ADR-0023](0023-the-screen-checks-ownership-not-behaviour.md) 으로 `claimView` 를 세우고,
"네트워크를 기다리는 함수는 표를 받는다" 를 CI 가 보게 했다. 그 검사는 일한다 — PR #30
에서 `openProblem` 이 표를 받지 않은 것을 **사람보다 먼저** 찾았다.

그런데 그 뒤로 나온 결함은 전부 **표를 받은 채로 틀렸다.**

```
통을 잘못 나눔        nextProblem 과 problem 을 따로 둠           PR #30
떠날 때 놓지 않음     showPicker · showSkills                     PR #30
예외 목록이 틀림      createUser 를 "화면 조각이 아니다" 로 제외    PR #30
같은 사용자의 세대     복습 · 진단 · Skill 표                      PR #29 · #30
지키는 축이 모자람    problem identity vs submission identity      PR #32
```

ADR-0023 의 한계 목록이 실제 사례를 따라 다섯 줄까지 늘었다. **정적 검사가 고를 수
있는 것은 "표를 받았는가" 하나뿐이고, 그 뒤의 판단은 정적으로 확인할 수 없다.**

## 결정

**두 층으로 나눈다.** 정적 검사를 버리지 않는다 — 가장 흔하고 싼 실수는 거기서 잡힌다.

```
WebClientTest      표를 받았는가 · 부르는 엔드포인트가 실재하는가     싸고 빠른 1차
Browser Races      늦게 온 응답이 최신 화면을 덮는가                 실제 동작의 2차
```

### 순서를 테스트가 쥔다 — 지연이 아니라 게이트로

`setTimeout` 으로 늦추는 것만으로는 부족하다. **수동 재현에서 두 번 실패했다** — 둘 다
늦게 보낸 응답이 먼저 도착해 경합 자체가 성립하지 않았다.

```js
const slow = gate();
route(url, async (r) => { await slow.held; r.fulfill(...); });  // 내가 놓을 때까지 잡는다
```

"몇 초 늦춘다" 로 쓰면 **조용히 통과하는 날이 생긴다.** 이 부류에서 가장 나쁜 결과다 —
검사가 있다고 믿는 것만 남는다. 그래서 `retries: 0` 이기도 하다. 재시도로 통과하면
정확히 그 결함을 숨긴다.

### 놓은 뒤에도 시간으로 기다리지 않는다

게이트가 보장하는 것은 **"언제 풀기 시작하는가" 까지다.** 그 뒤에 `waitForTimeout(300)`
으로 기다리면 같은 함정에 다시 빠진다 — 응답이 도착하고, body 를 읽고, 화면에 쓰이는
데까지 300ms 면 된다는 **가정**이다. 특히 "붙지 않았는가" 를 보는 검사는 아직 안 붙은
상태에서도 통과하므로 위험이 크다.

처음에 그렇게 썼고, 리뷰에서 잡혔다. 실제로 재현했다 — 결함을 되돌리고 늦은 응답이
500ms 뒤에 도착하게 하니:

```
waitForTimeout(300)   통과   틀렸는데 조용히
releaseAndSettle      실패   정확히
```

그래서 `releaseAndSettle` 이 순서로 기다린다. ① 늦춰 둔 응답이 실제로 도착할 때까지,
② 페이지에서 매크로태스크를 두 번 돌려 그 사이 마이크로태스크를 비운다 — `getJson` 이
body 를 한 번 더 읽으므로(`.json()`) 한 번으로는 부족하고, 화면을 쓰는 부분은 그 뒤의
동기 코드다.

**시간으로 기다리는 곳이 하나도 없다.** 첫 조회가 출발했는지도 시간이 아니라 요청
수를 세어서 기다린다.

### 백엔드를 띄우지 않는다

여기서 재현하는 것은 전부 화면 쪽이고, 서버가 무엇을 주는지는 이미 Java 쪽 294개가
본다. 진짜 서버를 쓰면 응답 순서가 큐와 DB 사정에 달려 결정적이지 않다.

대신 **모양이 서버와 갈릴 수 있다.** 실제로 처음에 `GET /api/submissions/{id}` 의
`result` 래퍼를 빠뜨려 화면이 영원히 "채점 중" 에 머물렀다. 그때 테스트는 그저
실패했고 **무엇이 틀렸는지는 말해 주지 않았다.**

### stub 은 `contracts/` 에 대고 검증한다

그래서 **응답을 내보내는 자리에서** 검증한다(`fixtures/contracts.js` 의 `fulfill`).
따로 "검증용 샘플" 을 두지 않는다 - 그러면 그것과 실제로 쓰는 응답이 갈리고, 이
저장소가 계속 만나온 패턴이 그것이다.

붙이자마자 **여섯 개가 이미 갈라져 있었다.**

```
state: "DONE"                 실제 enum 은 PENDING / COMPLETE   `!== "PENDING"` 이라 우연히 돌았다
problem-view 의 source        응답에 없는 필드
problem-view 의 skills.weight 내부 값이라 내보내지 않는다
/api/skills 와 users/{id}/skills  다른 계약인데 stub 하나가 둘 다 답했다
접수 응답(202)                submissionId 만 있고 state · result 가 없었다
problem() 호출 하나           title 누락
```

전부 "테스트는 통과하는데 서버와 다른" 것들이다. 첫 줄이 특히 그렇다 - 화면이
`state !== "PENDING"` 으로 보므로 `"DONE"` 도 그대로 돌았다.

**계약이 없는 응답은 이유와 함께 적는다**(`UNCONTRACTED`). `POST /api/users` 가
그렇다 - 계약을 만들지 여부는 API 쪽 결정이지 이 하네스의 결정이 아니다. 목록이
길어지면 규칙이 아니라 예외가 하네스를 지배한다.

**상태는 둘뿐이다 - 계약이 있거나, 이유가 있거나.** 처음에는 "계약을 아는데 검증은
안 한다" 는 제3의 상태를 `/run` 에 뒀는데, 그 경로는 **두 검사를 모두 비켜 갔다.**
리뷰에서 잡혔고 재현했다 - 그 상태에서는 `UNCONTRACTED` 의 이유를 통째로 지워도
여덟 개가 전부 통과했다. 예외를 표현하는 방법이 둘이면 그중 하나는 검사받지 않는다.

### 하네스 자신에도 대조군이 있다

검증은 **stub 이 그 문을 지날 때만** 일한다. `route.fulfill` 을 직접 부르면 조용히
우회되고, 남는 것은 "검사가 있다" 는 믿음뿐이다. 그래서 두 가지를 함께 본다
(`tests/stub-contracts.spec.js`).

```
우회하지 않는가       spec 파일에 route.fulfill( 이 없다
계약이 이어져 있는가   app.js 가 부르는 /api/ 경로가 전부 BY_PATH 또는 UNCONTRACTED 에 있다
```

뒤쪽은 `WebClientTest` 와 **다른 축이다** - 그쪽은 경로가 실재하는 매핑인지 보고,
여기서는 그 경로의 모양을 아는 계약이 있는지 본다.

### 각 시나리오에는 대조군이 있다

여섯 개 전부 **실제로 있었던 결함**이고, 그 fix 를 되돌려 테스트가 깨지는 것을 확인했다
(여섯 개 되돌림 → 여섯 개 실패). 이 저장소가 커리큘럼 검사에 메타테스트를 요구하는 것과
같은 규율이다 — **아무것도 안 잡는 E2E 를 두면 없는 것만 못하다.**

## ADR-0017 과의 관계

**갈음하지 않는다. 경계를 한 줄 좁힌다.**

ADR-0017 이 말한 것은 둘이었다.

1. 화면은 빌드 없이 정적 파일로 서빙한다
2. 두 번째 빌드 파이프라인을 들이지 않는다

**1번은 그대로다.** 화면은 여전히 `index.html` · `app.js` · `app.css` 셋이고 번들러가
없다. 이 PR 이 더하는 npm 의존성은 `e2e/` 안에만 있고, **배포물에 들어가지 않는다.**

2번에 예외를 하나 둔다 — **검증 도구**다. 그 근거는 위의 다섯 줄이고, 취향이 아니라
데이터다.

## 결과

- 사람이 찾았던 경합 여섯 개가 회귀 테스트가 됐다. 3.5초에 돈다
- 화면 파일이 바뀌면 CI 가 돈다. 경로 필터는 `static/**` 과 `e2e/**`

### 남는 위험

- **계약이 서버와 갈리는 것은 여전히 못 본다.** fixture 는 이제 `contracts/` 를
  지키지만, 그 계약이 컨트롤러와 맞는지는 Java 쪽(`contracts/` 대조 테스트)이 본다.
  두 축이 각각 도는 것이지 한 검사가 끝까지 잇는 것이 아니다
- **계약이 없는 응답은 검증되지 않는다.** `POST /api/users` 가 그렇고, 이유와 함께
  `UNCONTRACTED` 에 적혀 있다
- **새 경합을 자동으로 찾아 주지 않는다.** 이 층은 회귀를 막지, 아직 모르는 순서를
  탐색하지 않는다. 여전히 새 비동기 화면을 만들면 사람이 한 번은 눌러 봐야 한다
- 브라우저는 Chromium 하나다. 여기서 보는 것이 렌더링 차이가 아니라 비동기 순서라
  엔진을 늘려도 잡는 것이 늘지 않는다
