# ADR-0025 · 화면의 비동기 순서는 실제 브라우저로 검사한다

- 상태: 채택
- 날짜: 2026-09-13
- 정본 근거: [ADR-0017](0017-the-web-client-has-no-build-step.md),
  [ADR-0023](0023-the-screen-checks-ownership-not-behaviour.md)

## 맥락

[ADR-0023](0023-the-screen-checks-ownership-not-behaviour.md) 으로 `claimView` 를 세우고,
"네트워크를 기다리는 함수는 표를 받는다" 를 CI 가 보게 했다. 그 검사는 일한다 — PR #30
에서 `openProblem` 이 표를 받지 않은 것을 **사람보다 먼저** 찾았다.

그런데 그 뒤로 나온 결함은 전부 **표를 받은 채로 틀렸다.**

```
통을 잘못 나눔        nextProblem 과 problem 을 따로 둠           PR #30
떠날 때 놓지 않음     showPicker · showSkills                     PR #30
예외 목록이 틀림      createUser 를 "화면 조각이 아니다" 로 제외    PR #30
같은 사용자의 세대     복습 · 진단 · Skill 표                      PR #29 · #30
지키는 축이 모자람    problem identity vs submission identity      PR #32
```

ADR-0023 의 한계 목록이 실제 사례를 따라 다섯 줄까지 늘었다. **정적 검사가 고를 수
있는 것은 "표를 받았는가" 하나뿐이고, 그 뒤의 판단은 정적으로 확인할 수 없다.**

## 결정

**두 층으로 나눈다.** 정적 검사를 버리지 않는다 — 가장 흔하고 싼 실수는 거기서 잡힌다.

```
WebClientTest      표를 받았는가 · 부르는 엔드포인트가 실재하는가     싸고 빠른 1차
Browser Races      늦게 온 응답이 최신 화면을 덮는가                 실제 동작의 2차
```

### 순서를 테스트가 쥔다 — 지연이 아니라 게이트로

`setTimeout` 으로 늦추는 것만으로는 부족하다. **수동 재현에서 두 번 실패했다** — 둘 다
늦게 보낸 응답이 먼저 도착해 경합 자체가 성립하지 않았다.

```js
const slow = gate();
route(url, async (r) => { await slow.held; r.fulfill(...); });  // 내가 놓을 때까지 잡는다
```

"몇 초 늦춘다" 로 쓰면 **조용히 통과하는 날이 생긴다.** 이 부류에서 가장 나쁜 결과다 —
검사가 있다고 믿는 것만 남는다. 그래서 `retries: 0` 이기도 하다. 재시도로 통과하면
정확히 그 결함을 숨긴다.

### 백엔드를 띄우지 않는다

여기서 재현하는 것은 전부 화면 쪽이고, 서버가 무엇을 주는지는 이미 Java 쪽 294개가
본다. 진짜 서버를 쓰면 응답 순서가 큐와 DB 사정에 달려 결정적이지 않다.

대신 **모양이 서버와 갈릴 수 있다.** 실제로 처음에 `GET /api/submissions/{id}` 의
`result` 래퍼를 빠뜨려 화면이 영원히 "채점 중" 에 머물렀다. 그건 **이 층이 못 막는
것이고**, `WebClientTest` 도 경로와 method 만 대조하므로 막지 못한다. fixture 를 고칠
때 계약과 컨트롤러를 함께 보는 것이 지금의 유일한 방어다.

### 각 시나리오에는 대조군이 있다

여섯 개 전부 **실제로 있었던 결함**이고, 그 fix 를 되돌려 테스트가 깨지는 것을 확인했다
(여섯 개 되돌림 → 여섯 개 실패). 이 저장소가 커리큘럼 검사에 메타테스트를 요구하는 것과
같은 규율이다 — **아무것도 안 잡는 E2E 를 두면 없는 것만 못하다.**

## ADR-0017 과의 관계

**갈음하지 않는다. 경계를 한 줄 좁힌다.**

ADR-0017 이 말한 것은 둘이었다.

1. 화면은 빌드 없이 정적 파일로 서빙한다
2. 두 번째 빌드 파이프라인을 들이지 않는다

**1번은 그대로다.** 화면은 여전히 `index.html` · `app.js` · `app.css` 셋이고 번들러가
없다. 이 PR 이 더하는 npm 의존성은 `e2e/` 안에만 있고, **배포물에 들어가지 않는다.**

2번에 예외를 하나 둔다 — **검증 도구**다. 그 근거는 위의 다섯 줄이고, 취향이 아니라
데이터다.

## 결과

- 사람이 찾았던 경합 여섯 개가 회귀 테스트가 됐다. 3.5초에 돈다
- 화면 파일이 바뀌면 CI 가 돈다. 경로 필터는 `static/**` 과 `e2e/**`

### 남는 위험

- **stub 의 모양이 서버와 갈릴 수 있다.** 위에 적은 그대로이고, 지금은 사람이 맞춰야
  한다. 계약 스키마로 fixture 를 검증하는 것이 다음 단계다
- **새 경합을 자동으로 찾아 주지 않는다.** 이 층은 회귀를 막지, 아직 모르는 순서를
  탐색하지 않는다. 여전히 새 비동기 화면을 만들면 사람이 한 번은 눌러 봐야 한다
- 브라우저는 Chromium 하나다. 여기서 보는 것이 렌더링 차이가 아니라 비동기 순서라
  엔진을 늘려도 잡는 것이 늘지 않는다
