# ADR-0055 · case 는 하네스 혼자인 컨테이너에서 시작한다 - 앞 case 가 남긴 프로세스는 죽이고 거둔다

- 상태: 채택
- 날짜: 2026-09-27
- 정본 근거: Addendum §51(`--pids-limit 64`), §61(제출당 컨테이너 하나, 그 안에서 case 순회),
  [ADR-0005](0005-judge-stops-at-first-failure.md), [ADR-0015](0015-failure-shape-is-the-independent-evidence.md),
  [ADR-0053](0053-process-limit-is-per-container-not-per-uid.md)

## 맥락

하네스는 채점 컨테이너의 PID 1 이다(ENTRYPOINT, `--init` 없음). 사용자 프로세스가 자식을 두고 끝나면 그
자식은 PID 1 에게 넘어온다. 하네스는 제 자식만 기다렸다(`os.wait4(proc.pid, 0)`). ADR-0053 의 남는 위험에
적어 둔 결함이다.

case 마다 자기 말고 남아 있는 프로세스를 적는 제출로 main 의 하네스를 몰아 봤다(`pids` 는 cgroup 의
`pids.current`, 그 case 의 프로세스와 하네스 · 타이머 스레드를 포함한다).

| case | 옛 하네스 | 고친 하네스 |
| --- | --- | --- |
| 1 상태 확인 | pids 3 · 좀비 0 | pids 3 · 좀비 0 |
| 2 fork bomb | fork 61 번 | fork 61 번 |
| 3 상태 확인 | **pids 64 · 좀비 61** | pids 3 · 좀비 0 |
| 4 fork bomb | **fork 0 번** | fork 61 번 |
| 스레드 4 개로 푸는 case | **`RUNTIME_ERROR`** (`can't start new thread`) | `OK` |
| 60 초 사는 자손 55 개를 두고 끝난 case 다음 | **살아 있는 자손이 그대로 남는다** (실측 예: pids 63 · 60, 재검증에서는 58 · 55) | pids 3 · 0 |

좀비만이 아니다. **살아 있는 자손도 다음 case 로 넘어갔다.** 그래서 판정이 원인이 아닌 case 에 붙었다.

- **좀비가 자리를 차지한다.** fork bomb case 뒤에는 하네스 · 좀비 61 · 자식 · 타이머 스레드로 64 가 다 차서,
  혼자 돌리면 `ACCEPTED` 인 case 가 스레드 4 개를 못 만들어 `RUNTIME_ERROR` 가 났다.
- **늦게 쓰는 자손의 출력이 다음 case 의 출력에 섞였다.** 0.15 초 뒤 `LATE` 를 쓰는 자손을 둔 case 의 다음 또는 다음다음(타이밍에 따라)
  case 의 stdout 이 `8\n\x00\x00\x00\x00\x00LATE` 였다 - 같은 경로의 파일을 다시 열어(`wb`) 잘라도 자손은 제
  오프셋에 쓴다(NUL 개수는 실행마다 다르다). 호스트는 그것을 그 case 의 `WRONG_ANSWER` 로 읽는다.
- **자리를 계속 채우는 자손이 남으면 사용자 코드가 우리 잘못이 된다.** `setsid` 로 빠져나가 빈 자리를 계속
  채우는 자손을 둔 case 다음에서 하네스가 타이머 스레드를 못 만들고 죽었다(`RuntimeError: can't start new
  thread`). 호스트는 `SYSTEM_ERROR`("case 2 응답이 없다")를 돌려준다. ADR-0053 에서 한 번 본 C++ fork bomb
  의 `SYSTEM_ERROR`("case 4 응답이 없다")가 이것인지는 **확인하지 못했다** - 같은 C++ fork bomb 을 15 번(case
  60 개), 한 컨테이너에서 30 case 돌려도 다시 나오지 않았다. 앞 case 의 타이머 스레드가 아직 끝나지 않은 채
  다음 case 가 시작되면(`timer.cancel()` 은 끝날 때까지 기다리지 않는다) 좀비 61 과 합쳐 한 자리가 모자란다 -
  가능한 경로이지만 추측이다.

제출 하나가 제 case 를 망친 것이니 "어차피 그 제출의 잘못" 이라고 볼 수 있다. 그렇지 않다 -
**failedCaseId 와 실패의 모양(ADR-0015)이 원인이 아닌 case 를 가리킨다.** 실패의 모양은 Reviewer 주장을
확정하는 독립 근거이고, `SYSTEM_ERROR` 는 사용자가 아니라 우리 잘못이라는 판정이다.

## 결정

**case 가 끝나면 하네스가 컨테이너 안의 나머지 프로세스를 전부 죽이고 거둔다**(`_clear_leftovers`).

```text
os.wait4(proc.pid)      이 case 의 자식을 먼저 거둔다 - 종료 상태와 자원 사용량은 여기서만 받는다
timer.cancel() + join   타이머 스레드가 끝날 때까지 기다린다
kill(-1, SIGKILL)       pid namespace 안에서 나와 init 을 뺀 전부. 하네스가 init 이므로 컨테이너의 나머지 전부
waitpid(-1) ~ ECHILD    죽은 것은 전부 PID 1 에게 넘어오므로 좀비까지 거둔다
kill(-1) 이 ESRCH 일 때까지 되풀이
그다음 출력을 읽는다    자손이 멈춘 뒤라 읽은 값이 그 case 의 것으로 굳는다
```

- 일반 수거(`waitpid(-1)`)는 **자식의 wait4 뒤에만** 한다. 먼저 하면 자식의 종료 상태와 `ru_maxrss` 를 가져가
  버린다. 기다리는 동안 SIGCHLD 처리나 수거는 넣지 않았다 - case 안에서 쌓이는 좀비는 그 case 의 몫이고, 판정도
  그 case 에 붙는다.
- `kill(-1)` 은 `setsid` · `setpgid` 로 프로세스 그룹을 빠져나간 자손도 잡는다. 컨테이너 안은 전부 uid 10001
  이라 capability 없이 보낼 수 있다(`--cap-drop ALL` 그대로).
- **PID 1 이 아니면 아무것도 하지 않는다.** 컨테이너 밖에서 하네스를 직접 돌리면 `kill(-1)` 이 그 사용자의
  프로세스 전부를 죽인다.

고른 이유와 버린 것:

| 선택지 | 판단 |
| --- | --- |
| **하네스가 case 뒤에 `kill(-1)` + 수거** | 채택. 좀비와 살아 있는 자손을 함께 치우고, 컨테이너 옵션을 바꾸지 않는다 |
| `docker run --init`(tini) | 버림. 좀비만 거둔다. 옛 하네스에 `--init` 을 붙여 재 보니 좀비는 0 이 됐지만 살아 있는 자손 55 개가 다음 case 로 넘어갔고(하네스를 빼고 센 값), 늦은 출력이 섞였고, 자리를 채우는 자손 뒤에서 같은 `SYSTEM_ERROR` 가 났다. tini 가 자리를 하나 차지해 fork 도 60 번으로 줄었다. 하네스가 PID 1 이 아니게 되어 위 결정도 쓸 수 없다 |
| 자식을 새 세션으로 띄우고 `killpg` | 버림. 자손이 `setsid` 한 번으로 빠져나간다 - 위 측정의 "자리를 채우는 자손" 이 그렇게 했다 |
| 기다리는 동안 `wait4(-1)` 로 전부 수거 | 버림. 자식의 상태는 같게 받을 수 있지만 살아 있는 자손은 치우지 못하고, case 사이 문제는 case 뒤 수거로 충분하다 |

`DOCKER_LIMITS` 와 `MOUNT_MODE` 는 바꾸지 않았다. `--pids-limit 64` 는 그대로 64 이고 하나의 case 가 쓸 수
있는 양도 그대로다 - 바뀐 것은 앞 case 가 쓴 것을 돌려받는 것뿐이다.

## 검사

`test_judge.py` 의 **case 사이에 남는 프로세스** - 한 제출이 입력으로 갈린다. case 1(`leave`)은 60 초 사는
자손 10 개와 곧 끝나는 자손으로 자리를 채우고 끝나며, 끝나기 직전 남아 있는 프로세스 수를 적는다. case 2~4
는 스레드 8 개로 풀고, 자기와 PID 1 말고 남은 것이 있는지 적는다. 셋 다 `ACCEPTED` 여야 한다.

- **상태로 게이트한다.** case 1 이 55 개 이상 남기지 못했으면 `[VACUOUS]` 로 실패한다(실측 61). 오래 사는
  자손은 60 초를 자므로 뒤 case 가 도는 동안 스스로 사라지지 않는다. 시간을 맞춰 기다리는 곳이 없다.
- **fix 를 되돌리면 깨진다.** main 의 하네스로 세 이미지를 실제 태그에 구워 3 번 돌려 3 번 모두 case 2~4 가
  `RUNTIME_ERROR`(`can't start new thread`)로 실패했다. 되돌린 뒤 고친 하네스로 다시 구웠다.
- 하네스가 PID 1 이 아니게 되면(예: 누가 `--init` 을 붙이면) 이 검사는 하네스 자신을 "남은 프로세스" 로 세어
  실패한다. 그때는 수거가 꺼진 것이므로 실패가 맞다.

## 남는 위험

- **case 안에서** 사용자 코드가 하네스보다 먼저 64 를 다 채우면 하네스가 그 case 의 타이머 스레드를 못 만들고
  죽는다(`SYSTEM_ERROR`). 자식을 띄운 직후 스레드를 만들므로 경주다. 곧바로 자리를 채우고 쥐는 C++ 제출을 15 번
  (case 60 개) 돌려 한 번도 나오지 않았다 - 없다는 뜻은 아니다. 타이머를 스레드 대신 `setitimer` 로 두면 자리가
  필요 없지만, 이번 결함과 따로 재현한 뒤 바꾼다. → [ADR-0056](0056-the-time-limit-takes-no-slot-and-one-place-reaps.md)
  에서 게이트로 재현하고 `setitimer` 로 바꿨다.
- 자식이 끝난 뒤 `kill(-1)` 이 닿기 전까지 자손이 쓴 출력은 그 case 의 출력에 들어간다. 그 틈은 전보다 훨씬
  좁지만(다음 case 까지 → 수거까지) 0 은 아니다. 다음 case 로는 더 이상 넘어가지 않는다.
- **수거 루프 자체에는 상한이 없다.** 멈추면 호스트의 `SUBMISSION_HARD_TIMEOUT_S`(30 초)와 `docker rm -f` 가
  `SYSTEM_ERROR` 로 끊는다. `kill(-1)` 은 대상이 전부 EPERM 이면 0 을 돌려줘 루프가 끝나지 않지만, uid 10001 하나 ·
  `no-new-privileges` · `--cap-drop ALL` 아래에서는 그런 프로세스를 만들 수 없다.
- 검사는 Python 제출로만 본다. 수거는 하네스 한 곳에 있고 세 이미지가 같은 하네스를 굽지만, C++ · Java 로 같은
  조건을 만든 검사는 없다.
